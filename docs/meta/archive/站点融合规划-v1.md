## 三、硬约束与解法

| 约束 | 忽略的后果 | 解法 |
|---|---|---|
| `_site/` 不入库 | 手改产物 = 部署即丢 | 只改 `build_wiki.py` 与 `docs/` 源 |
| `md_pages` 是白名单 | 新 md 不登记就不生成页面 | 独立 `build_rules_page()`，不污染白名单 |
| 新 HTML 自带 `<html><head><style>` | 整页嵌进 shell → 嵌套文档、样式污染全站 | 只抽 `<figure>` 块内联；规则正文走 md |
| SVG 浅色硬编码 vs 深底 | 白块刺眼、深字不可读 | **纸卡容器**：figure 保留米底，SVG 一字不改 |
| 独立页含相对链接 | 站内指向 `战场玩法.html` → 404 | 生成时剥离该 `<p>` |
| 导航 93 链接平铺 | 新页沉底找不到 | 新增「玩法」组置顶 |
| SW 预缓存只有骨架 | 新页离线首访不可用 | `CORE` 增列新页 |

**为什么不改 SVG 配色**：深色化需改 5 张图约 60 处 `fill` / `stroke`，且会与已验收的独立页分叉成两套矢量。纸卡容器让「一份图源、两种主题」同时成立，改动量从 60 处降到 0 处；视觉上等同深色页面里贴一张图纸，不是把两种主题硬揉在一起。

## 五·补 移动端适配

主人追加的硬要求。原站点的 `@media (max-width:760px)` 只做了「侧栏改横排 + 字号缩小」，在 375px 下有三处硬伤：

| 硬伤 | 实测 | 解法 |
|---|---|---|
| 图解不可读 | 680 viewBox 被压到约 317px，缩放 0.47，图内 11px 字只剩约 5px | `figure.diagram` 改横滑，`svg{min-width:620px}`，加「左右滑动查看全图」提示；独立页同步处理 |
| 导航淹没首屏 | 93 条链接 inline 平铺，要点到正文得先滑过约半屏 | 侧栏改 sticky 一行 + 「目录」按钮；`.nav-inner` 默认收起，展开后限高 60vh 内部滚动 |
| 触摸目标过小 | 链接约 29px 高 | `.nav-toggle` 与导航链接 `min-height:44px` |

另补：`viewport-fit=cover` + `env(safe-area-inset-*)`（iOS PWA 全屏安全区）、`apple-mobile-web-app-capable`、`-webkit-text-size-adjust:100%`、`overflow-wrap:anywhere`、`.grid` 移动端改单列。原写「独立页 `docs/战场玩法.html` 有独立样式表，必须与站点同步改」已失效：图源改名为 `site/figures.html`，只作 SVG 唯一出处、无独立样式表，移动端样式全由 `build_wiki.py` 内联样式表统一生成，不存在「只修一半」。

**375×812 实测**（Edge 无头 + 375px iframe 读真实 DOM；直接用无头窗口截图会被 Windows 最小窗口宽度撑到约 500px，产生假裁切）：

| 指标 | 结果 |
|---|---|
| 整页 `scrollWidth` / `clientWidth` | 360 / 360，无横向溢出 |
| 折叠态 | `aside` 高 61px；「目录」按钮 inline-block；`nav-inner` 为 none |
| 展开态 | `max-height` 487px，`scrollHeight` 4157px，95 条链接在区内滚动 |
| 图解横滑 | `figClientW` 330 / `figScrollW` 640 / `svgW` 620，图内字保持约 10–13px |
| 触摸目标 | 44px |

**口径更正（后续裁定）**：主人否决横滑。现行实现为宽／竖双版矢量——同一 `<figure>` 内放桌面宽版与手机竖版各 1 张，媒体查询切换，整页零横向滚动；`min-width:620px` 与「左右滑动查看全图」提示已全部移除。上表「图解横滑」一行仅作当时实测留痕，不再是现行方案。

## 九、概念地图与同步契约

### 9.1 三层同步口径

| 层 | 由谁负责 | 是否自动 |
|---|---|---|
| 概要 → 网页正文 | `site/dashboard.md` 经 `parse_dashboard()` 切片 + `md_html` 在发布期生成 | 自动 |
| 正源章节 → 展开详情 | `site/concept-map.json` 指针 + 构建期 `slice_section()` 注入 | 自动 |
| 正源 → 概要文字 | 人工抽炼 | **不自动，唯一漂移点** |

站点本来就是**每次发布动态生成**（`pages.yml` → `build_wiki.py` → `_site` → Pages，`_site/` 不入库）。缺的不是「发布时生成」，而是「概要与正源之间的语义映射」没有机器约束。所以不采用「改完靠 AI 记住去同步网页端」的做法，而是把概要降级为指针：**能自动的自动，不能自动的让构建失败并点名位置**。

### 9.2 机制

1. `site/concept-map.json`（原 `docs/meta/概念地图.json`）：6 个概念、26 个锚点，每条只写 `{doc, section}`，**不复制任何规则文字**；`pages` 登记 10 篇正源对应的站内页。
2. `docs/tools/concept_map.py`：按 `## 标题` 切片（含其下 `###` 子节），`md_html` 转写后内联进**内层** `<details class="concept">`（26 个，可多开）；外再套 **6 个** `<details class="drawer" name="concept">`（原生互斥、同时只开一个）。两层都是原生 `<details>`，无 JS、无网络请求、PWA 离线可用；抽屉内顺序固定「极简概要 → 图解 → DDD 正源逐节折叠」。
3. 三重硬校验：锚点不唯一或缺失 → `ConceptMapError`；`pages` 指向的站内页未生成 → `check_pages` 拦死链；CI 另有独立 step `python docs/tools/concept_map.py --check` 让失败原因在日志里单独成行。**另加单页门禁**：6 抽屉 / 26 refs / 26 报告锚点 / 26 正源块 / 26 条原文链接，五项不等即 `BUILD FAILED`。
4. `CLAUDE.md` 新增「站点发布契约」：AI 每次改 `docs/ddd/**` 或 `docs/json/**` 后读到的硬规则，明确哪些改动无需同步、哪些必须更新 `concept-map.json`（**注：该节已于 2026-11-20 同步为 `site/` 三份源，见《站点Dashboard部署约束-v1》§六**）。
5. 构建期打印**同步报告**：26 个锚点各带章节正文 sha256 前 8 位与字数；正源一改，指纹立变，无需人肉比对。

由此：改章节**内容** → 下次发布自动同步；改章节**标题／删章节／加概念** → push 后 Actions 直接红，报错点名「哪篇文档哪一节」，AI 或人照着改指针表即可。
