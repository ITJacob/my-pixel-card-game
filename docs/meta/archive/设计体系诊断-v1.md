### 2.6 32 原语与 16 触发点的实际覆盖率

| 封闭集 | 声明数 | 实测使用数 | 覆盖率 | 未使用项 |
|---|---:|---:|---:|---|
| 效果原语（A：全库所有 dict，含顶层 Def 池） | 32 | **30** | 30/32 = 93.75% | **`disarm`、`recover_equipment`** |
| 效果原语（B：仅 `cards[].effects` 递归 / 仅卡整对象） | 32 | **28** | 28/32 = 87.5% | **`disarm`、`modify_damage`、`recover_equipment`、`target_override`** |
| 触发点（卡级 event+hook） | 16 | **9** | 9/16 = 56.25% | **`on_apply`、`on_attack`、`on_equipment_equip`、`on_phase_change`、`on_remove`、`on_spawn`、`on_turn_end`**（7 个） |
| 触发点（全库含 Def 池） | 16 | **15** | 15/16 = 93.75% | **`on_equipment_equip`**（1 个） |

**「32 原语中未被任何卡使用的分支」以口径 B 为准，共 4 个：`disarm`、`modify_damage`、`recover_equipment`、`target_override`。** 其中 `modify_damage`（全库 3 次）与 `target_override`（全库 4 次）只出现在文件顶层 Def 池（statusDefs / unitDefs / zoneDefs / domainDefs）的载荷里，不进入任何卡的效果树。外部复算的「distinct 28 种」对应口径 B；本文 §2.2 的分布表为口径 A（全库 1698 节点）。两口径同时给出，避免把「Def 池内出现」误当成「卡上使用」。

## 5. 若按现状实现，第一处会卡住的地方

**结论：不在运行时算法，而在「加载 Catalog 后第一条界域结算链」——`domain` 原语解引用不到 `domainDef`。**

证据链（按实现顺序）：

1. `ddd/README.md` 第 22 行（`INV-3` 快照隔离）与第 21 行（整场战斗一个 Combat 聚合）要求实现者先把全部定义态 Def 快照进战斗内；`tools/status_loader.py` 是这条链的实际加载入口（`POOLS` 五池）。
2. 加载 76 个文件后，会遇到 `family_06.skills.json` 的 `j03_edict_reality_rise`、`j03_abolition` 与 `hero_03.skills.json` 的 `h03_bedrock_rules`：每张卡的 `domain` 原语 `def` 与卡 `domain` grant 的 `def` 共 6 处，分别指向 `reality_press` / `edict_seal` / `order_bedrock`（§2.5 明细）。

### 核查点 3：manifest.cardCount 口径

**结论：与 `meta/SCHEMA.md` §1 口径一致，且逐项差 0。**

- `docs/json/manifest.json` 实测 9 条 `factions`，`cardCount` 之和 **307** = faction 文件 54 卡 + family 文件 253 卡；9/9 逐项差 0（明细见 §2.1）；不含 hero 层 264 卡，也不含 global 层 0 卡。

- 机器层补充证据：`docs/json/schema/manifest.schema.json` 的 `factions[].id` pattern 为 `^faction_[0-9]{2}$`、`file` pattern 为 `^faction_[0-9]{2}\.skills\.json$`，从结构上就排除了 family / hero / global 文件被登记；`factions` 只有 `minItems: 1`、**无 `maxItems`**，所以「只有 9 条」是数据现状与文档约定，不是 schema 上限。
- `tools/validate_schema.py` `cross_check()` 第 3 项只校验 faction 文件 ↔ manifest 对齐；`tools/validate.py` 用同一口径（`len(cards) + fam_sum`）复核，两者实测均 0 差异。
