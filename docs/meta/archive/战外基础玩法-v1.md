## 〇、这份文件管什么（5 行）

玩家是战前把英雄与一队英雄装配进槽、带进战斗的人。
场景是战外的名册与装配界面、以及战斗前的种子生成，不是战场本身。
反复做的事：按种子取一名英雄 → 绑定家族 → 从已解锁卡里挑主动/被动装槽 → 排站位 → 进入战斗。
想再做一次，是因为换一组装配与站位，同一套敌方配置会打出不同的开局账。
赢/输仍由战斗内核判定（敌方全部离场 / 己方全部离场），本文件不改写胜负口径。

## 一、边界与不变量对齐

- **本文件是设计规格，不是实现**。当前仓库没有游戏主程序、没有构建产物、无可运行画面，只有 7 个门禁脚本（`docs/meta/现状盘点-v1.md` L13–L17）。原项目把战外写在实现目录里，那是它的工程结构，不是本仓库的能力。
- 战斗内核**只读本文件的产出**（一次装配结果），不反向依赖战外；战外也不反向污染 `docs/ddd/` 的措辞（`CLAUDE.md` L3、L9）。
- **不新增原语、触发点、卡型或状态类别**：效果原语 32 个、触发点 16 个是封闭集（`CLAUDE.md` L17；INV-17/18）。战外生成结果只用既有承载体落成开局状态——常驻状态蓝本、初始属性修正（溯源账本）、初始被动槽，三选一或组合；禁止为任何战外概念开新效果类型。
- **INV-6 无手牌**：不引入抽牌 / 手牌 / 抽发机制。装配 = 从已解锁卡里**选装**，不是抽卡。
- **INV-9 无游离装备**：不引入背包 / 拾取 / 锻造；装备只能由装备牌创建、只存在于单位槽位。
- **INV-2 / INV-3**：一次生成由种子决定，生成过程在战斗外；内核只接收固定初始状态与输入次序，纯函数契约与 Catalog 快照隔离不被破坏。
- **INV-4 零随机伤害**：战外「按种子绑定家族」不是战斗内随机，不改伤害数值与目标选择的零随机约束。
- **R1–R6**：生成用种子须显式、可播种、可快照，与战斗种子同一登记口径（`docs/ddd/contexts/随机性治理.md`）；不在战斗内引入第二个随机源。
- 全文不写实现细节、代码类型名、数值锚点（`CLAUDE.md` L9）。

## 二、英雄生成（原 §5.1 重写）

**一次生成 = 种子 → 四元组 { 三维分配型, 初始禀赋条目, 家族, 初始被动槽 }。** 四项都由种子决定，玩家随后手工编排主动槽（装配见 §三）。

- **三维**：力量 / 敏捷 / 智力。当前 `docs/ddd/params/编队参数.md` L47 把位格列为独立维度，不参与三维分配。
- **分配型枚举**：三维各 ≥0、和值取 3，非负整数解恰好 **10 种**。原 §5.1 L141 用的也是这个和值。为什么取 3：解数恰为 10，生成空间有限可穷举、同种子可复现，且不会出现全维拉满的无效解；取更大的和值只会把「选谁」摊薄成一串近似解。
- **初始禀赋条目族 = 10 项**，与 10 种分配型同构。为什么是 10：把生成结果压成一张 10×10 可穷举表，回归时能逐格断言。**但原 §5.1 L142–L146 只给了「10 种」这个数量和三条落点，没给任何一项的名称与效果——等于没给条目清单**；本文件不替它编造，10 项的名称、效果与数值均不在此登记（见 §七）。
- **落点纪律**：初始禀赋不新增原语，只经既有承载体表达——常驻状态蓝本 / 初始属性修正 / 初始被动槽，三选一或组合。理由：把这三类都收敛到已有蓝本与已有槽位，Godot 实现方不需要为战外概念新建任何结算入口。
- **出生即写死、战内只读的两项**：性别、初始锚定值。理由：若允许战内改写，同种子同输入不再逐位相同，INV-2 直接破。
- **冲突裁定**：原 §5.1 L141 把「三维和 = 3」当属性生成约束；当前 `docs/ddd/params/编队参数.md` L47 未给该约束，且位格是独立维度。**以当前为准**：和值 3 只约束战外生成时的分配型枚举，不写成内核属性约束，也不登记进 `docs/ddd/`。它不是卡面数值锚点，不落入 `docs/meta/迁移缺口.md` §二 L117 的后置范围。

## 三、家族绑定与技能装配（原 §5.2 重写）

- **家族来源**：从已解锁家族中按种子取一绑定。当前 `CLAUDE.md` L15：9 派系 → 22 家族 → 英雄；家族 = 公共技能池 + 私有蓝本池 + 英雄容器，是当前 v2 承接旧里程碑 22 类身份的容器。原 §5.2 L152 的 22 类旧称谓按去 IP 改写为「22 家族」。
- **两套槽，分离不混**：主动槽装主动 / 装备 / 召唤卡（统一竞争牌位）；被动槽装被动卡（触发钩子 + 持续修正）；普攻与移动是不占卡位、0 能量的特殊行为槽。这套三分结构当前 `docs/ddd/contexts/编队上下文.md` L32–L36 已有，属于可迁的**结构**，本文件继承，不重复定义。
- **过滤条件**：轴（axis）/ 稀有度（rarity）/ 性别（gender）三项；作用域沿用 `docs/ddd/params/编队参数.md` L14「编队只从本派系文件组 + global 取卡」。理由：三项都是已有字段，不需要新字段也不需要新谓词。
- **冲突裁定（最关键）**：原 `game/DESIGN.md` L91–L92 与 §5.2 L153 给死了「每英雄 ≤4 主动槽 + ≤4 被动槽」的具体槽数。当前 `docs/meta/待办.md` §二 L25 明写「技能槽位数未定（8 槽方案弃用倾向），平衡期定」；`docs/meta/玩法分析与建议-v1.md` 建议 3 L272/L302 的 8 槽只在**建议层**、`docs/ddd/` 未动；`docs/meta/设计体系诊断-v1.md` §4.2 L296 明确「不采用任何具体槽位数字」。**以当前为准：槽位数一个都不迁，本文件不出现任何槽数**。同理，英雄私有卡是否占主动槽、是否可卸，当前属未定义边界（`docs/meta/设计体系诊断-v1.md` §4.2 L296），本文件一并留白，不替平衡期拍板。
- **明确不做**：抽发、构筑树、背包、卡池解锁的具体条件（原项目也不承载，见 `docs/meta/玩法迁移对齐-v1.md` §二 b1–b4、§三 G1）。

## 四、站位（原 §5.3 重写）

- 站位 = 把参战英雄分入路；`index 0` 恒为对峙前线；占用恒为**前缀无空洞**（INV-22 坍缩即时紧凑，`docs/ddd/README.md` L50）。理由：先手排序、转向、区域触发都按占位前缀推导，留内部空洞会让这三条规则同时失真。
- 一切占位变更只经 Placement（INV-21 唯一占位出口，`docs/ddd/README.md` L49）；换路不得跨阵营、不得越中线；目标路已满则插入被拒（`docs/ddd/contexts/战场上下文.md` §默认主动移动 L23–L28）。理由：占位只有一个写口，战外拖拽与战内位移才不会产生两套坐标口径。
- **冲突裁定**：原 §5.3 L157 给「每阵营 2 路 × 4 格」「5 英雄分入 2 路」；当前 `docs/ddd/contexts/战场上下文.md` §空间结构 L7 只说「Lane 是定长线性队列」，未登记容量数值；`docs/meta/迁移缺口.md` §一 P0-4 L74 把战场查表数值列为未迁，`CLAUDE.md` L9 禁数值锚点进 `docs/ddd/`。**以当前为准：队伍人数、路数、每路容量一律不迁**，本文件只保留上面三条几何规则；容量口径由当前战场契约与后续平衡标定决定。

## 七、本文件登记的数值与「为什么是这个数」

| 数值 | 理由 |
|---|---|
| 三维和值 = 3 | 三维各 ≥0、和为 3 的非负整数解恰 10 个；取最小可行和值使生成空间有限可穷举、同种子可复现，且不出现全维拉满的无效解。仅约束战外分配型枚举，不写成内核属性约束（§二） |
| 10 种三维分配型 | 上一条的直接结果；10 种是可逐格回归的最大有限集，超过 10 种会把「这次生成是谁」摊薄成近似解 |
| 10 项初始禀赋条目 | 与 10 种分配型同构，把生成结果压成 10×10 可穷举表；条目名称与数值属数值锚点，按 `docs/meta/迁移缺口.md` §二 L117 的 🔵 后置政策不在此登记 |
| 两套槽（主动 / 被动） | 不是新数值：当前 `docs/ddd/contexts/编队上下文.md` L32–L36 已分出主动槽 / 被动槽 / 特殊行为槽三型，本文件只继承其中两套的装配职责 |
| 榜单 ≥2 个可比较维度 | 少于两项无法排序；胜负与用时是无需新增字段即可取得的两项，其余维度属平衡期细化 |

**明确不登记**：槽位数、队伍人数、路数、每路容量、能量全局回复速率、`Pool.max`、`regen` 档位与扣费先后。前四项以当前 `docs/meta/待办.md` L25「未定」为准；后三项原项目也不承载（`docs/meta/玩法迁移对齐-v1.md` §二 b9–b11），硬填等于拍脑袋。

## 十、明确不做的事

- 不做地图 / 节点 / 事件 / 商店 / 关卡波次 / 敌人数值曲线 / 成长曲线 / 死亡分布（原项目也不承载，见 `docs/meta/玩法迁移对齐-v1.md` §三 G1–G4）。
- 不做抽发 / 构筑树 / 背包 / 拾取 / 锻造（INV-6 / INV-9，且原项目不承载）。
- 不写代码、不做美术风格决定、不定技术方案（不写接口类型名、目录名、端口、存储、构建、部署、联机）。
- 不替平衡期拍板槽位数与能量三条常量；不替主人决定「要不要做这个游戏」。
- 不把「原项目已实现」当成「当前项目已具备」。玩法是否好玩，最终只能由真人在真机上手玩判断；本文件只保证「规则自洽、曲线不崩」这层，而这一层当前因缺战外与关卡**尚未闭合**（`docs/meta/玩法分析与建议-v1.md` L29、L67）。
