# 编目上下文

> Catalog = 全部定义态 Def 的唯一聚合（不可变）。战斗启动时整体快照进战斗内（INV-2/3）。

## 聚合内容

- **技能卡**（SkillDef）：四种卡型——active（主动）/ passive（被动）/ equipment（装备牌，武器/护具两槽）/ summon（召唤牌，引用 unitDef 蓝本）。卡按**四层作用域文件**分属：家族公共卡归 family 文件，英雄独自卡归 hero 文件（归属由所在文件定，卡上不带归属字段）。
- **状态蓝本**（StatusDef）、**单位蓝本**（UnitDef，召唤物）、**区域蓝本**（ZoneDef）、**界域蓝本**（DomainDef）。
- 跨派系共享状态入 `global.skills.json`（全域级公共池）。

## 四层作用域与 $extends 继承

文件四层（每文件统一五池：cards/statusDefs/unitDefs/zoneDefs/domainDefs，均可空）：

```
global.skills.json       全域级（唯一）：跨派系复用内容
faction_NN.skills.json   派系级：家族间共享蓝本池（当前为空；cards 恒空）
family_NN.skills.json    家族级：家族公共卡（jNN_ 前缀）+ 家族私有蓝本池 + familyId/familyName/faction 元信息
hero_NN.skills.json      英雄级：英雄独自卡（hNN_ 前缀）+ family 归属字段
```

- **引用解析序（四层链）**：hero 文件 → 本文件 → family 文件 → 同派系 faction 文件 → global（family 文件 → 本文件 → faction 文件 → global）。状态/单位/界域/区域引用与 $extends 父定义均按此序解析。
- **$extends**（五池条目均可带）：声明式继承父定义。物化规则：逐字段浅合并（子字段存在即覆写）；`tags` 取父∪子并集（继承语义核心——扩展带父级 tag 供效果查询）；嵌套对象整体替换，不做深合并。父定义在同名池内按解析序查找；**禁同层跨文件** $extends（hero_01 不得继承 hero_02 / family_01 的条目）。
- manifest 只登记 faction 文件；family/hero/global 按文件名约定发现。

## 派系、家族与英雄（v2 框架）

```
派系（Faction）= 家族容器 + 家族间共享蓝本池（同派系多家族共用才入；源于九源质，9 派系封闭）
家族（Family）= 家族公共卡池 + 英雄容器
英雄（Hero）= 玩法骨架声明 + 独自技能全集
```

- 家族编号 family_01..22 为源质分组序封闭集（登记见 `docs/meta/SCHEMA.md` §1）；每家族先 1 英雄，后续可加英雄，新英雄自动共享家族公共技能。
- 家族 = 旧里程碑的**职业**（22 途径一一对应：warrior/assassin/…/prisoner），英雄 = 旧里程碑的**轴玩法**（一条轴一个英雄）。原 faction 文件的派系公共卡已原 id 迁入对应 family 文件（jNN_ 前缀，j 释义为家族）；蓝本池 2026-11 按归属归还——家族独占定义入 family 文件，faction 文件只留家族间共享蓝本（当前为空）。
- 英雄承接「一条轴的玩法」：玩法骨架（playstyle 一句话）+ 独自技能全集；hero 文件 `family` 字段指向所属家族。
- 数据落点：`docs/json/faction_NN.skills.json` + `family_NN.skills.json` + `hero_NN.skills.json` + `global.skills.json`；索引 `manifest.json`；结构标准 `docs/json/schema/skills.schema.json`。

## Def → Grant → Instance 全链（以状态为例）

1. **Def**（编目态，不可变）：默认值、机制标签、触发器声明。
2. **Grant**（派发值对象，不可变）：实例参数覆写（时长/层数/参数槽），一次派发一份。
3. **Instance**（战斗内实体）：剩余时长/层数/charges 等可变状态；卸载时按溯源回滚修正。

装备/界域/区域同构：EquipmentDef→Grant→Instance、DomainDef→Grant→Instance、ZoneDef→Grant→Instance。

**EquipmentDef 不建独立池——卡即 Def**：装备牌（kind=equipment）的卡 id 就是 EquipmentDef id，载荷（slot/attack/durability/armor/tags/modifiers/triggers）就是 Def 字段。原因：① INV-9 无游离实例——装备只能由装备牌创建、只存在于单位槽位，不存在「等待被装备的定义态物品」；② 一卡一件、无蓝本复用需求（区别于 unitDef：多张召唤卡可共用同一蓝本）；③ 卡与 Def 合一消灭同步面——抽成两池就要对账。界域/区域走独立 Def 池，正因为它们是无宿主实体、不由卡承载。若未来出现一卡多变体/装备模板复用，再抽离不迟。

## 引擎无关契约

- schema 是结构的唯一权威；实现（当前里程碑外）按 schema + DDD 语义重建。
- 卡面文本分层：`name`/`describe` 面向玩家；机制参数全部结构化，不解析自然语言。
