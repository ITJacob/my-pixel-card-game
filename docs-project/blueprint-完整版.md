## 〇、这份文档回答什么

你已经有一套成熟的**战斗内核**领域模型（7 个上下文 / 50 条不变量）。但那只是"一场战斗"。
一份能上架 Steam 的爬塔游戏，战斗内核大概只占总工作量的 **25%**——真正吃掉工期的是跑图、构筑、养成、UI 演出、数据内容与数值平衡。

本文档要解决的问题：**把剩下那 75% 也用 DDD 的方式切干净，让它和已有的战斗内核无缝咬合，而不是长成一团互相 import 的泥巴。**

三条贯穿全文的主线：

1. **战斗内核是被复用的资产，不是被扩展的对象。** 单人爬塔、人机、人人三种模式，都只是"往同一个战斗内核里灌不同的输入"。
2. **领域层必须能在没有 Godot 的情况下跑起来。** 这是数值平衡、AI 批量模拟、回放验证、自动化测试的前提，也是你喊"AI 协助"能真正兑现的前提。
3. **随机性治理从战斗内核上提为全局铁律。** 地图、掉落、事件、商店全部纳入同一种子体系，否则线上 bug 无法复现。

### 4.2 集成模式矩阵

| 上游 → 下游 | 集成模式 | 传递物 | 关键约束 |
|---|---|---|---|
| Progression → 战斗内核 | **快照（Snapshot）+ 防腐层 ACL** | `BuildSnapshot`（每单位 4 主动 + 4 被动） | 战斗启动后 progression 变更不影响进行中战斗；引擎零感知 rarity/weight/pool |
| Roster → 战斗内核 | **快照 + 防腐层** | `CombatParty`（单位 + 属性 + 初始站位 + 装备派生） | 站位映射在 ACL 完成，战斗内只认 Slot/Coordinate |
| Run → 战斗内核 | **命令 + 事件** | 入：种子 + 敌组配置 + 环境修正；出：`CombatEnded` | Run 不得读取战斗内部状态，只能通过结算摘要 |
| 战斗内核 → Run | **领域事件** | `CombatEnded{ result, turns, damageDealt, survivors }` | 最终一致；Run 收到后才推进奖励流程 |
| Draft → 各消费者 | **开放主机服务（OHS）** | `DraftRequest` → `OfferSet` → `Selection` | Draft 不认识技能/遗物，只认 `OfferItem`（多态） |
| Event → Roster/Run | **回执命令（Result Command）** | `EventOutcome.commands[]` | 事件上下文**不得直接写**其他聚合；产出命令由应用层执行 |
| Match → 战斗内核 | **快照**（同 Roster）+ 同步协议 | 同 Roster，外加 `ruleset` | 所有客户端同一 seed + 同一输入序列 → 同一结果 |
| 战斗内核 → Telemetry | **领域事件（异步）** | 结构化战斗日志 | 不参与战斗一致性，可丢弃 |
| Meta ← Run/Match | **领域事件** | `RunEnded` / `MatchEnded` 摘要 | Meta 不得反向影响进行中的 Run |

### 4.3 一条铁律：跨聚合写操作必须走应用层

**任何两个聚合之间，不允许直接持有引用互相修改。**

正确姿势：
```
UI 点击 → 应用服务（用例）→ 加载聚合A → A.产生领域事件/结果对象 → 应用服务加载聚合B → B.应用变更 → 提交事务
```

错误姿势（会让代码在 3 个月内不可维护）：
```
EventOption.apply(hero)   # 事件直接改英雄，跨聚合强耦合
```

事件、战斗奖励、商店购买——这三处是跨聚合写操作的高发区，全部产出**命令对象**交给应用层分发。

## 五、已有资产如何接入（重要）

### 5.1 战斗内核：整体作为"复用资产"下沉

你现有的 7 个上下文（战场 / 编队 / 调度 / 执行 / 效果 / 编目 / 随机性治理）**内部结构一个字都不用改**。
需要改的只有一件事：**给战斗内核定义清晰的对外的"入口契约"和"出口契约"**。

```
【入口】CombatSetup（值对象，不可变）
  ├─ combatSeed          : 战斗专用种子（从 Run/RunSeed 派生，不直接用主种子）
  ├─ catalogSnapshotRef  : 启动时快照的 Catalog 版本引用
  ├─ factions[]          : 每个阵营的单位清单
  │    ├─ UnitSetup { unitDefId, attributes, initialCoordinate }
  │    └─ BuildSnapshot { slots[] }  ← 来自 Progression
  ├─ environmentModifiers[] : 环境修正（来自 Run 的全局修正 / 事件 buff）
  └─ ruleset            : 回合上限 / 超时判定等

【出口】CombatEnded（领域事件）
  ├─ result      : victory | defeat | draw | timeout
  ├─ turns       : 回合数
  ├─ stats       : 伤害/治疗/承伤/技能使用次数（供 Telemetry 与结算展示）
  ├─ survivors[] : 存活单位及剩余生命
  └─ replayRef   : 回放数据引用（用于复现与平衡分析）
```

**这条契约一旦冻结，战斗内核就可以被三种模式同时复用，且可以独立测试、独立平衡、独立重构。**

### 5.2 肉鸽派发上下文：建议一分为二

你现有的「肉鸽派发」混了两件事，职责边界不清晰：

| 现有内容 | 问题 | 建议归属 |
|---|---|---|
| SkillDef 派发元信息、BuildAxis、BuildSlot、BuildSnapshot、UpgradeTrack、duplicatePolicy | ✅ 纯**构筑结构**，职责清晰 | **Progression（构筑）** |
| rarity / weight / pool 的**抽取机制** | ❌ 文档只定义了字段，没定义"三选一怎么生成"；而且遗物/药水/商店/宝箱都需要同一套机制 | **Draft（抽发）** |

**为什么值得拆**：

1. **复用面完全不同。** 抽发机制不只给技能用——遗物掉落、商店货架、宝箱、事件奖励、升级选择，全部是"从池里按权重抽 N 个，玩家选 1 个"。做成独立上下文，一套算法 + 一套 UI 吃全部场景。
2. **变化频率完全不同。** 抽发算法（保底、去重、权重曲线）是稳定的；构筑槽位规则会随内容迭代频繁变。混在一起会导致改动互相污染。
3. **确定性要求不同。** 抽发要严格可复现（bug 复现靠它），构筑是玩家显式操作的历史，本来就是确定的。

**拆分后**：`Draft` 负责"抽"，`Progression` 负责"装"，Run/Event/战斗奖励都是客户。

详见 [`contexts/progression-构筑.md`](./contexts/progression-构筑.md) 与 [`contexts/draft-抽发.md`](./contexts/draft-抽发.md)。

## 六、关键架构决策（ADR 摘要）

| # | 决策点 | 推荐方案 | 理由 | 状态 |
|---|---|---|---|---|
| **ADR-01** | 语言分工 | **C# 核心逻辑层（Domain + Application）+ GDScript 表现层**，中间设 `GameBridge` 防腐层 | C# 保住批量模拟与强类型红利；GDScript 保住 UI 热重载速度——**UI 是改得最频繁的部分**，而 C# 改动需重建程序集。两者各得其所。跨语言边界见 [04 篇](./04-CSharp与GDScript跨语言边界.md) | ✅ **已定** |
| ADR-02 | 领域层与引擎耦合 | **零依赖**：不继承 Node、不引用 Godot 命名空间 | 是 ADR-01 红利的前提；也是 AI 协助编码能被自动验证的前提 | ✅ **已定** |
| **ADR-03** | 联机同步拓扑 | **确定性锁步**（只同步输入 + 种子） | 战斗内核已是纯函数 `f(初始状态, 输入序列, 种子)`，天然适配；**且已确认无牌库 → 无隐藏手牌信息，锁步最难的信息屏蔽问题不存在**；零服务器成本 | ✅ **已定**（PvP 排 M8） |
| ADR-04 | 内容数据格式 | **JSON/CSV 源文件 + 导入器**，不用 `.tres` | 可 diff、可 code review、AI 可批量生成与改写；.tres 二进制冲突无解 | ✅ 建议采纳 |
| ADR-05 | 结算与演出解耦 | **领域瞬时结算 + 事件队列 + 表现层异步播放** | 卡牌游戏 UI 第一难点。领域一次性算完，UI 慢慢演出，否则动画会撕裂一致性边界 | ✅ 建议采纳 |
| ADR-06 | 存档 schema | **版本化 JSON + 显式迁移器** | 上线后改数据结构是必然，无版本化必毁档 | ✅ 建议采纳 |
| ADR-07 | 全局随机性 | **单主种子派生全部子种子**（地图/掉落/事件/商店/战斗各自派生） | bug 可复现、回放有效、AI 模拟可重放；是测试与平衡的基础设施 | ✅ 建议采纳 |
| ADR-08 | PvP 排期 | **M8，不在首发** | 复杂度最高、ROI 最低，先做能单人上线的部分 | ✅ **已定** |

# 第3篇：01-上下文地图与集成

# 01 · 上下文地图与集成契约

> 本篇定义**上下文之间怎么说话**。比"每个上下文内部长什么样"更重要——90% 的架构腐化发生在边界上，而不是内部。

---

## 一、上下文分类与守护强度

| 类别 | 上下文 | 守护强度 | 说明 |
|---|---|---|---|
| **战斗内核**（一组强内聚上下文） | 战场 / 编队 / 调度 / 执行 / 效果 / 编目 / 随机性治理 | 🔒 最强 | 内部上下文之间有共享的一致性边界（整场战斗一个聚合），对外只有一个门口 |
| **独立核心上下文** | 抽发 / 构筑 / 跑图 / 事件 / 名册 | 🔒 强 | 各自独立聚合，通过应用服务编排 |
| **支撑上下文** | 对局匹配 / 元进度 / 平衡遥测 | 🔓 中 | 可用现成方案，允许较松的边界 |
| **共享内核** | 值对象 / 规约 / 随机源 / 元素 / 术语 | ⚠️ 危险区 | 改动成本最高，只放"几乎不会变"的东西 |

### 关于"战斗内核是一组上下文，不是一个"

这点要特别说清楚，容易踩坑：

你现有文档里，战场/编队/调度/执行/效果 是**同一个聚合（Combat）内部的逻辑分层**，不是五个独立聚合。它们之间没有事务边界，可以直接互相访问，一致性由 Combat 根统一保证。

所以对外而言，**战斗内核 = 1 个聚合 + 1 个 Catalog 聚合 + 1 个横切随机性治理**。Catalog 是独立聚合（定义态，只读），随机性治理是横切关注点（提供 `RandomSource` 端口实现）。

```
外部视角的战斗内核：
   ┌─────────────────────────────────────────┐
   │  Combat 聚合（唯一入口：CombatSetup）     │
   │  ┌───────┬───────┬───────┬──────┬─────┐ │
   │  │ 战场  │ 编队  │ 调度  │ 执行 │效果 │ │  内部自由访问
   │  └───────┴───────┴───────┴──────┴─────┘ │
   └─────────────────────────────────────────┘
             │ 读                    │ 事件
             ▼                       ▼
      ┌────────────┐          ┌────────────┐
      │  Catalog   │          │  外部世界   │
      │（独立聚合）│          └────────────┘
      └────────────┘
```

**推论**：不要让 Run 直接读取战斗内部的 Unit 状态。想拿战斗结果，就订阅 `CombatEnded`。

---

## 二、防腐层（ACL）契约

防腐层是"外部世界 ↔ 战斗内核"之间的翻译器。它的职责是**阻止外部概念泄漏进内核，也阻止内核概念泄漏到外部**。

### 2.1 入口 ACL：`CombatSetupFactory`

职责：把 Roster / Progression / Run 的产物翻译成 `CombatSetup`。

```
输入侧（外部概念）                      ACL 翻译                     输出侧（内核概念）
───────────────────────────────────────────────────────────────────────────────────
Hero { heroId, level, attributes }  ─┐
Party { members, formation }        ─┤
BuildSnapshot { slots[] }           ─┼─▶ CombatSetupFactory ─▶ UnitSetup { unitDefId,
Inventory { relics[], items[] }     ─┤                          attributes,
Run.modifiers[]                     ─┤                          initialCoordinate,
Catalog snapshot                    ─┘                          behaviors[] }

EnemyGroup (来自 Run 节点配置)      ─────────────────────────▶ UnitSetup[]  (敌对阵营)
Run.seed + nodeId                   ──▶ SeedDeriver ─────────▶ combatSeed
```

**翻译规则（必须遵守）**：

| 外部概念 | 内核里必须变成 | 不允许的写法 |
|---|---|---|
| 英雄等级、装备、遗物加成 | 已求和进 `AttributeSet` 的最终值 | 把 `Hero` 对象塞进战斗 |
| 玩家站位（第几排第几个） | `Coordinate`（lane/slot） | 战斗内感知"队伍 UI 顺序" |
| 技能槽位 + 升级档位 | 已展开的 `BehaviorSlot[]`（含 tier 增量已应用） | 战斗内感知 `UpgradeTrack` / `tier` |
| 稀有度 / 权重 / 池 | ❌ 不进入内核 | 战斗内出现 rarity 分支 |
| 遗物触发效果 | 展开为被动 `BehaviorSlot` 或环境修正 | 战斗内查询 Inventory |

**一句话**：ACL 出口处，`CombatSetup` 里不应该有任何一个对象来自 Roster / Progression / Run 的命名空间。

### 2.2 出口 ACL：`CombatSummary`

战斗结束只吐摘要，不吐内部状态：

```
CombatEnded (领域事件)
  ├─ combatId
  ├─ result         : Victory | Defeat | Draw | Timeout | Abandoned
  ├─ turns          : int
  ├─ stats
  │    ├─ damageByUnit   : Map<unitId, int>
  │    ├─ damageTakenByUnit
  │    ├─ healingByUnit
  │    └─ behaviorUsage  : Map<behaviorId, count>   ← Telemetry 与平衡分析的主数据源
  ├─ survivors      : Array<{ unitId, hpRemaining }>
  └─ replayRef      : { seed, inputLogRef }          ← 确定性红利：一个种子+日志就能完整复现
```

> `replayRef` 是 ADR-03 的副产品。有了它，玩家报 bug 只需要发一个种子 + 输入日志，你就能百分百复现现场。
> 这个能力在独立游戏上线的头三个月能省下难以估量的排查时间。

## 三、跨聚合写操作规范（重点）

### 3.1 问题场景

这些地方天然需要"一次操作改多个聚合"：

| 场景 | 涉及聚合 |
|---|---|
| 事件选择"花费 50 金币，获得一个技能" | Run（扣金币）+ 抽发（生成候选）+ 构筑（填槽位） |
| 战斗胜利奖励 | 战斗（结束）+ Run（推进节点）+ 抽发（掉落）+ 名册（加经验） |
| 商店购买 | Run（金币）+ 名册（背包）+ 构筑（若是技能） |
| 战外招募英雄 | Run（资源）+ 名册（加英雄 + 队伍） |

### 3.2 规范：结果命令（Result Command）模式

**禁止**跨聚合直接持有引用修改。**强制**走"产生命令 → 应用层分发"：

```
❌ 错误：
   class EventOption:
       func apply(hero: Hero, run: Run):
           hero.add_skill(...)
           run.gold -= 50

✅ 正确：
   class EventInstance:
       func choose(optionId) -> EventResolved:
           # 事件聚合内部只做自己的事
           return EventResolved(
               outcome = ...,
               commands = [
                   ModifyResource { resource: GOLD, delta: -50 },
                   GrantDraftOffer { pool: SKILL_POOL, count: 3 },
                   GrantExperience { heroId, amount: 100 },
               ]
           )
   # 应用层：
   for cmd in event.commands:
       commandBus.dispatch(cmd)   # 每个命令自己加载对应聚合、校验、提交
```

**收益**：
- 事件数据（几十上百条）变成纯数据 + 声明式命令，可以被 AI 批量生成、非程序员编辑
- 每个命令是原子的、可测试的
- 事务边界清晰：一个用例 = 一个事务

### 3.3 事务边界

| 范围 | 事务 | 说明 |
|---|---|---|
| 单个用例（一次命令分发） | 一个事务 | 全成功或全回滚 |
| 一次节点结算（战斗 + 奖励 + 推进） | 一个事务 | 玩家不能"拿了奖励但节点没推进" |
| 一次战斗内部的结算步骤 | 强一致（战斗内核自己保证） | 已有设计 |
| 战斗 → Run / Telemetry | 最终一致（事件） | 允许短暂延迟 |

**存档时机**：只在**节点边界**落盘（进入节点前、节点结算后）。
战斗过程中不落盘——战斗是可重放的（种子 + 输入日志），落盘既慢又容易写入半截状态。

## 四、逐对集成关系详解

按"容易出事"排序。

### 4.1 抽发 Draft ← 被多方调用（最需要设计好）

Draft 是**被复用最多**的上下文，做成开放主机服务（OHS）：

```
               ┌─────────────────────────────────────┐
               │        Draft 抽发上下文              │
               │  OfferSet（聚合根）                  │
               │                                     │
               │  入：DraftRequest                   │
               │    { poolId, count, exclusion[],    │
               │      constraints, seed }            │
               │                                     │
               │  出：OfferSet                       │
               │    { items[], allowSkip, expiresAt }│
               │                                     │
               │  Selection → 已选项                 │
               └─────────────────────────────────────┘
                    ▲        ▲        ▲        ▲
         ┌──────────┘        │        │        └──────────┐
     技能三选一          遗物掉落   商店货架    宝箱/事件奖励
     (Progression)      (Roster)  (Run)      (Event)
```

**关键抽象 `OfferItem`**：Draft 不认识"技能"或"遗物"，只认识统一的报价项：

```
OfferItem
  ├─ itemId       : 多态标识（skill:xxx / relic:yyy / potion:zzz）
  ├─ itemType     : 枚举（供 UI 分派渲染器）
  ├─ rarity       : 稀有度（决定权重档与展示）
  ├─ weight       : 权重
  ├─ tags         : 用于约束过滤（pathway / buildAxis / chapter 等）
  └─ payloadRef   : 指向 Catalog 中真实定义的引用（Draft 不解析它）
```

**这一层间接是值得的**：Draft 的算法（保底、去重、权重）只写一次，UI 的"三选一面板"只做一次，然后所有场景复用。

### 4.2 跑图 Run ↔ 战斗内核

```
Run                                        战斗内核
 │                                              │
 │ 1. 玩家点击战斗节点                            │
 │ 2. 派生 combatSeed = derive(runSeed, nodeId)  │
 │ 3. 组装 CombatSetup ────────────────────────▶ │
 │                                              │ 4. 战斗推进（纯函数）
 │ 5. ◀──────────────────────── CombatEnded ────│
 │ 6. 结算：推进节点、触发奖励 Draft              │
 │ 7. 落盘（节点边界）                            │
```

**种子派生**（ADR-07）：
```combatSeed = Hash(runSeed, "combat", actIndex, nodeId)```
每个节点的战斗种子固定 → 玩家可以刷，但每次刷的都是同一个结果（这是爬塔游戏的正确行为，杀戮尖塔亦如此）。若想让 SL 大法失效，可加入 `attemptCount`，但**建议保持可 SL**，独立单机游戏不该为难玩家。

### 4.3 名册 Roster → 构筑 Progression

Roster 提供**槽位约束**（4 主动 + 4 被动来自 UnitDef），Progression 负责**填充**。两者通过 `Loadout` 值对象交换：

```
Roster.Hero ──────▶ LoadoutRequest { heroDefId, ownedSkillIds[] }
                            │
Progression 处理      ◀─────┘
   ├─ 校验：技能是否属于该英雄的途径（pathway 过滤）
   ├─ 校验：槽位是否饱和（INV-P2）
   ├─ 校验：重复获得策略（duplicatePolicy）
   └─ 产出：BuildSnapshot
                            │
Roster.Hero ◀──── Loadout { slots[], upgradeTiers[] }
```

**职责切分**：
- Roster 拥有"英雄有什么技能"
- Progression 拥有"这些技能怎么摆进槽位、怎么升级"
- Catalog 拥有"技能本体长什么样"

### 4.4 事件 Event → 外部（回执命令）

见 §3.2。事件是**纯数据驱动**的：

```
EventDef (Catalog)
  ├─ id, title, text
  ├─ conditions[]     : 触发条件（章节、生命值、金币、已拥有物…）
  ├─ weight           : 出现在事件池的权重
  ├─ onceOnly         : 是否一次征程只出现一次
  └─ options[]
       ├─ text
       ├─ requirements[] : 选项可见条件（有 50 金币 / 有某遗物…）
       ├─ previewHint    : 结果模糊提示（杀戮尖塔式）
       └─ outcomes[]     : 加权结果集
            └─ commands[]  : 结果命令
```

**事件上下文只做三件事**：求值条件、筛选项、掷骰选结果。**所有副作用都是命令，由应用层执行。**

### 4.5 对局 Match → 战斗内核（确定性锁步）

```
Client A                    同步层                    Client B
   │                          │                          │
   ├─ MatchFound(matchSeed) ──┤                          │
   │◀─────────────────────────┤─────────────────────────▶│
   │                          │                          │
   ├─ Input{turn:1, ops[]} ──▶│─────────────────────────▶│
   │                          │  交换双方输入              │
   │◀─────────────────────────┤◀─────────────────────────┤
   │                          │                          │
   ├─ 双方各自用同一 seed + 同一输入序列推进战斗          │
   └─ 结果必然一致（战斗内核是纯函数）                    │
```

**校验机制**：每个客户端定期广播状态哈希，不一致即判定作弊/失步。
**优势**：零服务器逻辑、带宽极低（只传操作）、天然支持回放。
**劣势**：无法防"读取对手隐藏信息"类作弊（需要额外做信息屏蔽）。

> 【待补】是否需要服务器权威取决于你对作弊的容忍度。独立游戏 PvP 用户量通常不大，锁步 + 举报机制一般够用。

## 五、共享内核的准入标准（严格）

共享内核是最危险的区域——改一行，所有上下文都受影响。

**准入测试**（必须全部满足）：

1. ✅ 至少 3 个上下文需要它
2. ✅ 它的语义在任何上下文里都**完全一致**（不是"差不多"）
3. ✅ 它在可预见的未来**不会频繁变化**
4. ✅ 它**不持有任何业务规则**（只有结构与计算）

**当前清单**：

| 成员 | 说明 | 是否满足 |
|---|---|---|
| `RandomSource` / 种子派生 | 全局确定性基石 | ✅ |
| `TargetSpec` / `EffectRef` / `EffectCondition` | 效果描述 | ✅（战斗内核已用） |
| 元素枚举 `Element` | 元素标签 | ✅ |
| 术语 `TermDef` | 数值术语 | ✅ |
| `Coordinate` / `Position` | 位置 | ⚠️ **风险**：战斗内是 lane/slot，战外是队伍 UI 站位，语义不同 → **不要共享**，各自定义，在 ACL 翻译 |
| `Rarity` | 稀有度 | ⚠️ 战斗中不使用，只在 Draft/Progression/Catalog → 可放共享内核但**禁止战斗内核引用** |
| `ResourceType`（金币/生命/钥匙） | 战外资源 | ⚠️ 只有 Run/Roster 用 → **不放共享内核**，放 Run 上下文 |

> **`Coordinate` 是个典型陷阱**。战斗内的"位置"是格子，战外的"站位"是队伍编排顺序，两者看起来像，实际语义和约束完全不同（格子有唯一占位约束，队伍站位是玩家偏好）。强行统一会导致两边都被污染。

## 六、上下文依赖检查清单

写代码时，用这几条做自检。任何一条违反，就是架构开始腐化的信号：

- [ ] 领域层任何文件都没有 `using Godot` / `extends Node`
- [ ] GDScript 侧搜不到除 `GameBridge` 以外的任何核心层类型名（跨语言唯一通道，见 [04 篇](./04-CSharp与GDScript跨语言边界.md)）
- [ ] 战斗内核命名空间下，搜不到 `rarity` / `weight` / `pool` / `gold` / `level` 这些词
- [ ] 没有哪个聚合直接持有另一个聚合的实体引用（只能持有 ID 或快照值对象）
- [ ] 跨聚合变更全部经过命令对象或领域事件
- [ ] 共享内核里没有业务规则（只有结构、计算、枚举）
- [ ] 所有随机都走 `RandomSource`，没有直接调 `rand()` / `Random.Range()`
- [ ] 所有跨上下文传递的对象都是不可变值对象或显式事件

> 建议把这份清单做成 CI 里的架构守卫测试（扫描命名空间交叉引用）。
> **这类自动化检查是"AI 协助编码"能放心提速的前提**——AI 写代码快，但也更容易把边界搞坏，机器能查的东西不要靠人盯。

# 第4篇：02-分层架构与Godot工程落地

# 02 · 分层架构与 Godot 工程落地

> 本篇回答：**代码放哪个目录、谁依赖谁、怎么保证不烂掉**。

---

## 一、四层架构

| 层 | 职责 | 能否引用 Godot | 能否被控制台程序引用 |
|---|---|---|---|
| **领域层 Domain** | 全部业务规则、聚合、实体、值对象、领域事件、不变量 | ❌ **禁止** | ✅ **必须能** |
| **应用层 Application** | 用例编排、命令分发、事务边界、存档单元、DTO 装配 | ❌ 禁止 | ✅ 必须能 |
| **基础设施层 Infrastructure** | 持久化、网络、资源加载、随机源实现、时钟、日志 | ✅ 可以 | ❌ |
| **表现层 Presentation** | Godot 场景、UI、动画、输入、音频、相机 | ✅ 可以 | ❌ |

**依赖方向（严格单向）**：
```
Presentation ──▶ Application ──▶ Domain ◀── Infrastructure
     └──────────────┴──────────────┘
              （基础设施实现 Domain 定义的接口，依赖倒置）
```

领域层定义接口（如 `IRandomSource`、`ICatalogProvider`、`IClock`），基础设施层实现。

---

## 二、语言分工（ADR-01 · 已定：方案 B）

> **结论（2026-09-04）**：**C# 写核心逻辑层（Domain + Application），GDScript 写表现层**，中间用 `GameBridge` 连接。
> 跨语言边界的完整设计见 **[04 篇](./04-CSharp与GDScript跨语言边界.md)**，本篇只记录选型结论与工程影响。

### 2.1 方案对比与选择

| 方案 | 批量模拟 | 脱离 Godot 跑 | 类型安全 | UI 迭代速度 | 选择 |
|---|---|---|---|---|---|
| A. 全 C# | ⭐⭐⭐⭐⭐ | ✅ | ⭐⭐⭐⭐⭐ | ⭐⭐（改一次要重建程序集） | |
| **B. C# 核心 + GDScript UI** | ⭐⭐⭐⭐⭐ | ✅ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐（热重载即改即见） | ✅ **已选** |
| C. 全 GDScript | ⭐⭐ | ⚠️ 能但很慢 | ⭐⭐ | ⭐⭐⭐⭐⭐ | |

### 2.2 为什么这个组合其实是最优解

关键不在性能，而在**改动频率与语言特性的匹配**：

| 层 | 改动频率 | 需要的特性 | 语言 |
|---|---|---|---|
| 领域层 / 应用层 | **低**（规则确定后很少改） | 性能、强类型、可脱离引擎测试 | **C#** |
| 表现层 | **极高**（UI 调参一天几十次） | 热重载快、写起来随手 | **GDScript** |

Godot 4 的 C# 改动需要重新构建程序集，没有 GDScript 那种即改即见的热重载。
把改得最凶的部分留在 GDScript，把最稳的部分放在 C#——**两边都拿到了自己最需要的东西**。

### 2.3 代价与对策

| 代价 | 对策 |
|---|---|
| GDScript 无法访问独立 .NET 类型 | `GameBridge`（C# Node，Autoload）作为唯一通道 |
| 自定义 `struct` / 泛型 / 枚举无法跨界 | Codec 编成 POD（整数 / 字符串 / 数组 / 字典） |
| Codec 样板代码量大 | 规则固定 → **交给 AI 生成** + 往返测试兜底 |
| 跨语言调用有 marshalling 开销 | 事件批量回传；禁止在 `_Process` 里跨语言调用 |

**这条边界是防腐层的物理实现**——GDScript 摸不到领域对象，是强制的架构纪律，不是限制。

### 2.4 关于"批量模拟能力"（选 C# 的核心理由）

**真正的理由不是性能本身，是"批量模拟能否形成反馈闭环"**。

你要做数值平衡系统和 AI 协助。这两个要成立，必须能：
```
for i in 0..100000:
    模拟一整场 AI vs AI 战斗
    统计胜率 / 回合数 / 技能使用分布
```
- GDScript 跑一场可能 100ms → 10 万场 = 2.8 小时，改一次数值等一晚上
- C# 跑一场可能 2ms → 10 万场 = 3 分钟，**可以放进 CI，每次提交都跑**

这不是"快一点"的差别，是"能不能形成反馈闭环"的差别。数值平衡的迭代速度直接决定游戏手感上限。

**次要理由**：
- 你已有 50 条不变量 + 9 种 effect types，强类型能把这些约束静态化，AI 生成代码时编译器就能挡掉一大半错误
- 领域层作为独立 .NET 类库，可以用 xUnit 做单元测试，CI 集成干净
- Steam Deck / Linux / Windows 全支持 .NET 8

**剩下需要注意的**：
- Godot C# 的导出配置比 GDScript 略麻烦（尤其 macOS 签名），需含 .NET 的导出模板
- 跨语言调用的 marshalling 与 Codec 样板代码是新增工作量 —— 详见 [04 篇](./04-CSharp与GDScript跨语言边界.md)

> **两条不能妥协的铁律**：
> 1. **领域类禁止继承 `Node`。** 一旦继承 Node，类就绑死在场景树上，无法在控制台里 new 出来，测试与模拟全废。
> 2. **GDScript 只能通过 `GameBridge` 触碰核心层。** 任何试图绕过桥直接摸领域对象的写法，都是在拆防腐层。

### 2.5 回应一个常见疑问：模拟器为啥要单独立项？领域为啥要独立成库？

> 这是讨论中真实被问到的问题，原话大意是：
> *"跑模拟可以另外起一个项目来做，把核心代码同步过去就行了，为啥要在这个项目里这么复杂的做个库？"*

**先给结论：你"单独起一个项目跑模拟"的直觉是对的，而且本方案正是这么做的**——`CardGame.Simulator/` 就是一个独立的控制台项目（见 §三 目录树）。它和 Godot 游戏**地位平等，都只是"领域层的一个消费者"**。

真正需要澄清的是两件事，别把它们混为一谈：

**① 模拟器单列 = 完全正确，无需争论。**
批量模拟（跑 10 万场 AI 对战做平衡）需要能脱离 Godot 的 CPU 环境。把它放进 Godot 项目里跑 headless 也能跑，但单独一个 `dotnet run` 的控制台项目更干净、能进 CI、不拖引擎依赖。**这一项直接采纳你的思路。**

**② "领域独立成库"不是在 Godot 里"额外加复杂度"，而是为了让"领域零 Godot 依赖"这件事被编译器免费担保。**

| 方案 | 领域代码放哪 | "零 Godot 依赖"怎么保证 | 会不会"同步漂移" |
|---|---|---|---|
| **A. 领域独立成库（本方案）** | 单独 `CardGame.Domain.csproj`，**不引用** GodotSharp | **编译器强制**：这个 csproj 里 `using Godot;` 根本编不过 | 不会。游戏和模拟器都 `ProjectReference` 引用**同一个**库，改一次两边都生效 |
| B. 领域散落在 Godot 项目里 | 作为 Godot 项目内的普通 `.cs` 文件 | **靠纪律**：开发者自觉不写 `using Godot;`；只能靠 CI 用 grep 兜底 | 同左，靠引用或 `<Compile Include>` 共享源文件，也不复制 |

关键点：**A 和 B 都不需要"把核心代码同步过去"**。无论是库引用还是共享源文件，都是"同一份代码被两个项目引用"，不是"复制两份再手动同步"。你说的"同步"是复制思路，那个才容易漂移——所以我们**根本不用复制**。

那 A 比 B 好在哪？就一点：**A 让架构红线变成编译错误，B 只能靠人盯。**
在方案 A 里，领域层 csproj 的物理依赖里没有 GodotSharp，任何人在领域文件里写 `using Godot;` 会**立即红字编不过**——零维护成本。在方案 B 里，领域文件混在 Godot 项目里，某天有人"图方便"在领域里 new 了个 `Node` 或读了 `Time`，游戏照常能跑，只有等你跑 Simulator 时才炸。**前者免费，后者靠自觉**。

> **所以"独立成库"不是给 Godot 项目加负担，恰恰相反：它把"领域必须干净"这条最重要的规矩，交给编译器去守，省掉你日后人工 code review 的精力。**
> 如果你就是想让目录更简单、领域文件直接躺在 Godot 项目里（方案 B），也完全可行，代价是加一条 CI 守卫脚本（扫领域文件里的 `using Godot;`，命中即失败）。结构更扁，红线更软，你按偏好选。

## 四、内容数据管线（ADR-04）

### 4.1 为什么不用 `.tres`

| 对比项 | Godot Resource (.tres) | JSON 源文件 |
|---|---|---|
| Git diff | 二进制/冗长，冲突无解 | 纯文本，diff 清晰 |
| Code Review | 基本没法审 | 可以审 |
| AI 批量生成/改写 | 困难 | **天然适配**（AI 直接读写 JSON） |
| 校验 | 弱 | 可挂 JSON Schema + CI 校验 |
| 运行时性能 | 略好 | 忽略不计（启动时一次性加载） |
| 策划/非程序员编辑 | 需要装 Godot | 任何文本编辑器 |

**对你这个项目的决定性理由**：你明确要"AI 协助"。内容量（几十个英雄 × 4 主动 4 被动、上百个事件、几百个技能）是最大的工作量，这块必须让 AI 能批量产出。JSON 让这件事变得可行，`.tres` 会让 AI 在格式上翻车。

### 4.2 管线

```
data/*.json  ──▶ [CI] JSON Schema 校验 + 引用完整性检查
                        │
                        ▼
              [运行时启动]  JsonCatalogLoader
                        │  解析 → 校验 → 建索引 → 冻结（不可变）
                        ▼
                    Catalog（只读、可缓存、可快照）
```

**Catalog 冻结后不可变**。战斗启动时做快照（`catalogSnapshotRef`），保证进行中的战斗不受配置变更影响——这条你已有设计，这里只是确认它同样适用于 JSON 管线。

### 4.3 数据校验（CI 必做）

内容数据是 bug 高发区，靠人眼查不现实：

| 检查项 | 说明 |
|---|---|
| Schema 校验 | 字段类型、必填、枚举取值域 |
| 引用完整性 | `behaviorTemplate` / `effectRef` / `poolId` 指向的 id 必须存在 |
| 数值区间 | 权重 ≥ 0、生命值 > 0、cost 在合法区间 |
| 构筑轴覆盖 | 每途径 4 轴，且覆盖全部技能（你已有约束，自动化检查） |
| 平衡哨兵 | 单技能理论 DPS 超阈值告警 |
| 孤儿检测 | 定义了但从未被任何池引用的技能 |

> 这些检查非常适合交给 AI 写，且效果极好——纯规则、纯结构，没有歧义。

## 五、确定性随机（ADR-07）

### 5.1 种子树

```
runSeed（玩家可见，可输入/分享）
  ├─ mapSeed      = Derive(runSeed, "map")
  ├─ draftSeed    = Derive(runSeed, "draft", nodeCounter)   ← 每次抽发递增
  ├─ eventSeed    = Derive(runSeed, "event", nodeId)
  ├─ shopSeed     = Derive(runSeed, "shop", nodeId)
  ├─ lootSeed     = Derive(runSeed, "loot", nodeId)
  └─ combatSeed   = Derive(runSeed, "combat", actIndex, nodeId)
```

**规则**：
1. 主种子派生一切，**任何地方都不允许直接 new Random()**
2. 每个子流独立计数，互不干扰（抽卡次数不影响地图生成）
3. 种子派生函数必须是**纯函数且跨平台一致**（用整数哈希，如 xxHash / SplitMix64，不要用字符串 Hash——不同运行时实现不同）

### 5.2 三个跨平台陷阱（血泪教训）

| 陷阱 | 后果 | 对策 |
|---|---|---|
| **浮点差异** | `0.1 + 0.2` 在不同平台/编译优化下末位不同 → 伤害差 1 点 → 战斗分叉 | 影响结果的判定**全部用整数或定点数**；必须浮点时，比较用 epsilon 且统一取整时机 |
| **集合遍历顺序** | `Dictionary` 遍历顺序不稳定 → 结算顺序随机 → 结果分叉 | 所有影响结算的集合用**有序结构**或显式排序；禁止依赖字典遍历顺序 |
| **字符串 Hash** | `.NET` 的 `string.GetHashCode()` **每次进程启动都不同**（随机化种子） | 种子派生只用整数/字节哈希，禁用字符串哈希参与随机 |

> 这三条任何一条踩中，都会出现"本地测试正常，玩家端偶发失步"的幽灵 bug，且极难定位。
> **建议在领域层里直接封掉危险 API**（提供 `Fixed` 定点数类型、有序集合封装），让 AI 和人都没有犯错的机会。

### 5.3 定点数建议

```csharp
// 领域层不要出现 float/double
public readonly struct Fixed : IEquatable<Fixed>, IComparable<Fixed>
{
    private readonly long _raw;          // 1.0 == 1 << 16
    public static Fixed FromInt(int v) => ...
    public static Fixed FromRatio(int num, int den) => ...
    public Fixed Mul(Fixed other) => ...  // 内部 (a*b) >> 16
}
```

战斗中的伤害、倍率、抗性全部走 `Fixed`。表现层再转 `float` 给动画用。

## 六、结算与演出解耦（ADR-05，卡牌游戏 UI 第一难点）

### 6.1 问题

领域层结算是**原子的、瞬时的**（一次结算步骤内全部变更强一致）。
但 UI 需要**逐个演出**（出牌 → 飞过去 → 闪一下 → 掉血 → 死亡 →…），耗时几秒。

如果 UI 边演出边驱动领域，就会出现：玩家狂点、动画没播完就结算下一张、中途退出导致状态半截。

### 6.2 解法：事件队列 + 异步追赶

```
领域层                              表现层
──────────────                     ──────────────
Action 结算（瞬间完成）
  └─ 产出 DomainEvent[]  ─────────▶ EventQueuePlayer
     CardPlayed                       │ 按序取出
     DamageDealt                      │ 播放动画（耗时）
     StatusApplied                    │ 播完 → 取下一个
     UnitDied                         │
     ...                              ▼
（领域已到达最终状态，               （表现层慢慢追，追上即一致）
 不再等待 UI）
```

**关键机制**：

| 机制 | 说明 |
|---|---|
| **输入闸门** | 队列非空时，UI 输入被冻结（或只允许"加速/跳过"） |
| **快进** | 玩家点加速 → 队列以 3× 速度播放；再点 → 瞬间跳完 |
| **追赶** | 玩家中途退出战斗 → 队列瞬间排空，领域状态已是最终态，直接落盘 |
| **回放** | 队列就是天然的分镜脚本，录制下来就是回放 |

**收益**：领域层完全不知道动画存在，可以 headless 全速跑；UI 只是"播放一段分镜"，状态永远收敛。

## 一、表现层（Presentation）

### 1.1 架构模式：MVVM + 命令

```
领域状态 ──▶ ViewModel（投影/缓存/通知） ──▶ View（Godot Control 节点）
                    ▲                              │
```

| 角色 | 职责 | 禁止 |
|---|---|---|
| **View** | 渲染、动画、输入捕获 | 直接改领域对象；持有业务逻辑 |

### 2.3 AI 生成美术的一致性挑战与对策

你明确要"AI 协助"，美术是最大的一块工作量。但 AI 生图最大的问题不是质量，是**一致性**——同一个角色的第 3 张图可能和第 1 张不像。

**对策组合**：

| 对策 | 做法 |
|---|---|
| **风格锚定** | 固定一组"风格参考图"作为每次生成的条件输入；所有资源共用同一份 prompt 前缀与负面词 |
| **角色设定表** | 每个角色写死一份结构化描述（发色/服饰/配色/体型），作为生成的固定约束 |
| **后处理流水线** | 统一量化到主色板、统一尺寸、统一描边、去背景 → 自动脚本批处理，抹平风格差异 |
| **分层生成** | 底框/UI 元素全部手工做一套模板，AI 只生成插图部分 → 一致性风险面最小化 |
| **人工把关点** | 关键资源（主角、Boss）人工终审，次要资源（小怪、图标）可以放宽 |

**建议的优先级**：**先把 UI 框架、卡面底框、图标体系手工定死**，AI 只填插图。
这样即使 AI 产出风格有波动，整体观感仍然是统一的——因为 80% 的画面面积是固定模板。

### 2.4 音频（顺带占位）

- AI 生音效已可用（但 BGM 仍建议找人或买授权）
- **务必早期确认音乐授权范围**（商用/流媒体），Steam 上线后出问题很麻烦

## 三、网络与联机

### 3.1 拓扑选型（ADR-03）

| 方案 | 服务器成本 | 防作弊 | 带宽 | 复杂度 | 适用 |
|---|---|---|---|---|---|
| **A. 确定性锁步（推荐）** | 零（P2P） | 弱 | 极低（只传输入） | 中 | 回合制卡牌 |
| B. 服务器权威 | 高 | 强 | 中 | 高 | 需要强反作弊 |
| C. 中继转发（Steam） | 零 | 弱 | 低 | 低 | 只想连通就行 |

**推荐 A + C 组合**：Steam 的 P2P 网络负责穿透与传输，业务层走确定性锁步。

**为什么锁步对你特别合适**：你的战斗内核已经是 `结果 = f(初始状态, 输入序列, 种子)` 的纯函数。这意味着：
- 不需要服务器跑战斗逻辑
- 只需同步"第 N 回合的操作"，带宽几 KB
- 断线重连 = 重新灌种子 + 重放输入日志
- 回放系统免费获得
- 反作弊只需比对状态哈希

**这是你已有设计的一个巨大红利，别浪费。**

### 3.2 锁步实现要点

```
每个回合：
  1. 双方各自生成本回合操作（本地，无需等待）
  2. 广播 Input{ turnNo, ops[], inputHash }
  3. 收到对方输入 → 双方用同一顺序应用两个输入 → 推进一回合
  4. 每 N 回合广播一次 stateHash，不一致 → 失步处理
```

| 问题 | 对策 |
|---|---|
| 一方掉线 | 等待超时 → 判负或托管 AI |
| 状态不一致 | 以种子 + 完整输入日志为准，强制重放 |
| 隐藏信息泄露（手牌） | 锁步下所有状态本地可见 → 需额外做**信息屏蔽层**：只同步"公开可见的效果结果"，隐藏信息用承诺-揭示协议 |
| 延迟 | 回合制对延迟不敏感，300ms 内体验良好 |

> **隐藏信息是锁步的真正难点**（不是同步，是防窥探）。
> 若 PvP 模式有手牌/牌库概念，需要专门设计"承诺-揭示"或者使用服务器权威。
> **这是把 PvP 排在 M8 的另一个理由**——它比看起来复杂。

## 四、持久化

### 4.1 三档存档

| 存档 | 内容 | 频率 | 丢失后果 |
|---|---|---|---|
| **Meta 存档** | 账号、解锁、成就、统计、设置 | 变更时 | 严重（玩家会投诉） |
| **Run 存档** | 当前爬塔进度（断点续玩） | **节点边界** | 中等 |
| **回放/日志** | 战斗输入日志 | 战斗结束 | 轻微 |

### 4.2 版本化 schema（ADR-06）

```json
{
  "schemaVersion": 7,
  "savedAt": "2026-09-04T14:00:00Z",
  "runSeed": 123456789,
  "payload": { ... }
}
```

**必须有的机制**：
- 每个存档带 `schemaVersion`
- 一组 `IMigration { from, to, Migrate(JObject) }`，启动时按序升级
- **存档前先写临时文件再原子替换**（防止写到一半崩溃毁档）
- 保留最近 N 个备份（玩家会手动回滚）
- 启动时校验失败 → 进入"安全模式"，提示玩家而不是直接崩

> 独立游戏最容易挨骂的就是毁档。上线后你一定会改数据结构，没有版本化迁移就是灾难。

### 4.3 存档防作弊

单机爬塔不需要强防作弊，但至少：
- 关键数值做校验和（防止手改存档导致崩溃）
- 异常值检测（金币负数、等级越界）→ 拒绝加载
- 别在防单机作弊上花时间，玩家改自己的存档不影响任何人

## 五、数值平衡系统（Telemetry）

### 5.1 三个层次

```
① 数据采集（游戏内）
   战斗日志 → 结构化指标 → 本地 SQLite / 文件
        │
② 批量模拟（离线 / CI）
   领域层 headless + AI 策略 → 10 万场 → 统计报告
        │
③ 分析看板
   胜率 / 回合数分布 / 技能选取率 / 稀有度强度曲线 / 死亡点分布
```

### 5.2 核心指标

| 指标 | 用途 | 健康区间【待补】 |
|---|---|---|
| **技能选取率** | 哪些技能没人要（废卡） | 目标：无 <5% 的技能 |
| **技能胜率贡献** | 哪些技能过强/过弱 | 各技能胜率极差 < ±8% |
| **构筑集中度** | 是否存在唯一最优解 | 前 3 构筑占比 < 50% |
| **阶层通过率** | 每层难度曲线 | 平滑下降 |
| **平均回合数** | 战斗节奏 | 目标 6~12 回合 |
| **死亡节点分布** | 难度尖刺定位 | 无明显尖刺 |
| **首通率/弃局率** | 新手友好度 | 弃局率 < 30% |

### 5.3 批量模拟的 AI 策略梯度

| 策略 | 用途 | 实现成本 |
|---|---|---|
| 随机策略 | 基线（下限） | 极低 |
| **贪心启发式** | 主力（性价比最高） | 低 |
| 一维搜索（枚举出牌顺序取最优） | 近似最优解 | 中 |
| MCTS / 自对弈 | 接近人类上限 | 高，M8 再说 |

**建议**：M6 阶段只做"随机 + 贪心"两个策略就够了。
贪心策略的胜率 vs 随机策略的胜率，两者差距就是"玩家技巧带来的收益空间"——这个差值本身就是一个极有价值的平衡指标。

### 5.4 与 AI 协助的结合

这是"AI 协助"最能发力的地方之一：

- **自动生成平衡报告**：定期跑模拟 → 让 AI 读统计 → 用自然语言总结"本周哪些技能偏离了目标"
- **自动调参建议**：给定目标胜率区间，AI 提议数值调整方案 → 人工审核后进入模拟验证
- **批量内容生成 + 自动初筛**：AI 生成 N 个技能 → 数据校验 → 批量模拟 → 筛掉明显失衡的 → 人工只审剩下的

> 最后一条是真正的生产力杠杆：**AI 生成 100 个，机器筛掉 80 个，人只审 20 个。**
> 前提就是架构上的 headless + 确定性 + 批量模拟能力。这也是为什么我在 ADR-01 里强烈推 C#。

# 第6篇：04-CSharp与GDScript跨语言边界

# 04 · C# 与 GDScript 跨语言边界

> **背景**：已定方案 —— **核心逻辑层（Domain + Application）用 C#，UI / 表现层用 GDScript**。
> **本篇解决**：这两层怎么说话。这是方案确定后**第一个会卡住开发的工程问题**，M0 阶段必须先打通。
> **状态**：🆕 本版新增

---

## 〇、先说结论：这个组合选得对

表面看是妥协，实际对独立游戏是**最优解**：

| 层 | 语言 | 理由 |
|---|---|---|
| 领域层 / 应用层 | **C#** | 性能（批量模拟快 1~2 个数量级）、强类型（50 条不变量静态保障）、可脱离 Godot 跑测试与模拟 |
| 表现层 | **GDScript** | **热重载快**。UI 是改得最频繁的部分，GDScript 改完即见；C# 改动需要重建程序集 |

**被低估的关键点**：改 C# 需要重新构建整个程序集，Godot 4 的 C# 热重载体验远不如 GDScript。
UI 迭代一次可能要调几十上百次参数——如果 UI 也是 C#，你每天会多花一小时在等编译上。
把高频迭代的部分留在 GDScript，把稳定的部分放在 C#，正好各自发挥所长。

代价就是本篇要解决的问题：**边界怎么处理**。这个代价是值得的，也是可控的。

---

## 一、硬约束（必须先接受的三条）

### 约束 1：GDScript 无法直接使用外部 .NET 类型

Godot 的 GDScript 只能识别**它自己扫描到的类型**（引擎内置类型 + Godot 项目内 C# 脚本编译出的类型）。

你的领域层是**独立 .NET 类库**（`CardGame.Domain.dll`），为了能在控制台跑批量模拟。
GDScript **看不到**里面的 `Combat`、`Fixed`、`EntityId<T>`、各种枚举和实体。

> 【待验证】Godot 4.x 各版本对"外部程序集类型可见性"的支持细节有差异。
> **无论结果如何，下面的 Bridge 层都是必须的**——理由见约束 2 和 3，它们与这条无关。
> M0 阶段用一个 5 行的最小样例验证即可（见 §七验证清单）。

### 约束 2：跨语言只能传 Godot 兼容类型

即便类型可见，C# 的自定义 `struct` / 泛型 / 领域实体也无法跨语言传递。
只能通过 **marshalling 白名单**：

| C# 类型 | GDScript 侧 | 是否可传 |
|---|---|---|
| `int` / `long` | `int`（64 位） | ✅ |
| `float` / `double` | `float` | ✅（但领域层禁用，见下） |
| `bool` / `string` | `bool` / `String` | ✅ |
| `enum` | ❌ → **转成 `int`** | ⚠️ 需显式编码 |
| `T[]` / `List<T>` | `Array` | ✅ |
| `Dictionary<K,V>` | `Dictionary` | ✅（key 需基础类型） |
| 自定义 `struct`（`Fixed`、`EntityId<T>`） | ❌ | ❌ **必须编码** |
| 领域实体（`Combat`、`Hero`） | ❌ | ❌ **必须编码** |
| `null` | `null` | ✅ |

**推论**：跨语言边界传递的只能是 **POD（Plain Old Data）**——数字、字符串、布尔、数组、字典，及其嵌套。

### 约束 3：GDScript 没有泛型、没有接口、没有自定义值对象

所以不要在边界上试图"传一个对象过去让 UI 自己读字段"。
**必须显式地把领域状态投影（Project）成 UI 友好的结构。**

## 二、架构：Bridge 层（唯一合法通道）

```
┌────────────────────────────────────────────────────────────┐
│  GDScript 表现层                                            │
│  场景 / UI / 动画 / 输入 / 演出队列                          │
└───────────────┬──────────────────────────▲─────────────────┘
                │ Command (POD)            │ Signal (POD 批量)
┌───────────────▼──────────────────────────┴─────────────────┐
│  ★ GameBridge（C#，Godot Node，Autoload 单例）              │
│    · 唯一允许被 GDScript 触碰的东西                          │
│    · 编码/解码 POD ↔ 强类型                                 │
│    · 持有 ApplicationFacade（应用层门面）                    │
│    · 不持有任何业务规则                                      │
└───────────────┬────────────────────────────────────────────┘
                │ 强类型调用
┌───────────────▼────────────────────────────────────────────┐
│  C# 应用层 → 领域层（纯 .NET，零 Godot 引用）                │
│  可被 CardGame.Simulator 控制台程序直接引用                  │
└────────────────────────────────────────────────────────────┘
```

**这条边界正好是防腐层的物理体现**——好处是：即使未来 Godot 支持了直接访问，GDScript 也不该直接摸领域对象。物理隔离强制了架构纪律。

## 三、下行：GDScript → C#（命令）

### 3.1 推荐做法：显式方法 + POD 参数

```csharp
// CardGame.Game/Bridge/GameBridge.cs
using Godot;
using Godot.Collections;

public partial class GameBridge : Node
{
    private ApplicationFacade _app;

    public override void _Ready()
    {
        _app = ServiceContainer.Build();   // 装配 Application + Domain + Infrastructure
    }

    // ✅ 显式方法：常用路径走这个，重构友好、可读性好
    public Dictionary ExecuteCommand(StringName commandName, Dictionary args)
    {
        try
        {
            var command = CommandCodec.Decode(commandName, args);  // POD → 强类型
            var result  = _app.Execute(command);                   // 进入领域层
            return ResultCodec.Encode(result);                     // 强类型 → POD
        }
        catch (DomainException ex)
        {
            return ResultCodec.EncodeFailure(ex.Code, ex.Message);
        }
    }
}
```

```gdscript
# UI 侧
var bridge := get_node("/root/GameBridge")

func _on_start_run_pressed(seed_value: int) -> void:
    var result: Dictionary = bridge.execute_command(&"StartRun", {"seed": seed_value})
    if result.get("ok", false):
        _enter_map_scene(result["data"])
    else:
        _show_error(result["error"])
```

### 3.2 不推荐：全动态字符串命令

`bridge.execute("some.typed.by.hand.string", {...})` —— 字符串拼错要到运行时才发现，重构即崩。
**只在极少数需要数据驱动的场景使用**（比如编辑器工具），主流程一律用显式方法。

> 折中：如果命令种类多（几十个），可以在 C# 侧把所有命令名生成为一个常量类 / 枚举，
> GDScript 侧引用常量，兼顾灵活与安全。

## 四、上行：C# → GDScript（领域事件）

### 4.1 批量发送（关键）

**绝不要逐条事件跨语言发送。** 一次战斗结算可能产生几十个领域事件，逐个 `EmitSignal` 会有明显的 marshalling 开销，且 UI 难以保证处理原子性。

```csharp
public partial class GameBridge : Node
{
    [Signal]
    public delegate void DomainEventBatchEventHandler(Array events);   // Array<Dictionary>

    private readonly List<Dictionary> _pending = new();

    // 领域事件总线订阅 → 先入队
    private void OnDomainEvent(IDomainEvent e)
    {
        _pending.Add(EventCodec.Encode(e));
    }

    // 一个用例执行完毕后，一次性冲刷
    private void Flush()
    {
        if (_pending.Count == 0) return;
        CallDeferred(MethodName.EmitBatch, _pending.ToArray());
        _pending.Clear();
    }

    private void EmitBatch(Array batch) => EmitSignal(SignalName.DomainEventBatch, batch);
}
```

```gdscript
func _ready() -> void:
    GameBridge.domain_event_batch.connect(_on_domain_events)

func _on_domain_events(events: Array) -> void:
    for evt in events:
        _event_queue.push(evt)     # 进入演出队列，逐个播放动画
    _event_queue.play()
```

**这样正好接上 02 篇 §6 的演出队列**：一次结算 = 一批事件 = 一段分镜。

### 4.2 事件编码格式

```gdscript
# 一个领域事件的 POD 形态
{
    "type": "DamageDealt",          # StringName
    "seq":  17,                     # 序号，用于排序与去重
    "data": {
        "sourceUnitId": 3,
        "targetUnitId": 7,
        "amountPermille": 1500,     # 定点数用整数传，不用 float
        "element": 2                # 枚举 → int
    }
}
```

## 五、ViewState：领域状态的只读投影

UI 需要"当前血量、手牌、冷却"这类状态。不要去摸领域对象，由 C# 侧**投影**成 POD：

```csharp
public Dictionary GetBattleViewState()
{

    return ViewStateCodec.Encode(snapshot);
}
```

```gdscript
# 每次收到事件批次后刷新一次，不要每帧调用
func _on_domain_events(events: Array) -> void:
    var view: Dictionary = GameBridge.get_battle_view_state()
    _hp_bar.refresh(view["units"])
```

**性能纪律**：

| 规则 | 说明 |
|---|---|
| ❌ 禁止在 `_Process` / `_PhysicsProcess` 里跨语言调用 | marshalling 开销会被放大到每帧 |
| ✅ 事件驱动刷新 | 收到事件批次 → 拉一次 ViewState |
| ✅ 纯动画用 GDScript 本地插值 | 血条平滑下降这类不要反复问 C# |
| ✅ 高频只读数据可缓存 | 在 C# 侧维护缓存副本，GDScript 直接读 |

## 六、编码/解码层（Codec）——唯一需要写样板代码的地方

这是本方案唯一的"体力活"。规则固定，所以**非常适合让 AI 生成**，也是 AI 协助的高收益点：

```csharp
public static class EventCodec
{
    public static Dictionary Encode(IDomainEvent e) => e switch
    {
        DamageDealt d => new Dictionary {
            ["type"] = "DamageDealt",
            ["seq"]  = d.Sequence,
            ["data"] = new Dictionary {
                ["sourceUnitId"]     = d.SourceUnitId.Value,   // EntityId<T> → int
                ["targetUnitId"]     = d.TargetUnitId.Value,
                ["amountPermille"]   = d.Amount.ToPermille(),  // Fixed → int（千分比）
                ["element"]          = (int)d.Element,         // 枚举 → int
            },
        },
        _ => throw new UnmappedEventException(e.GetType()),
    };
}
```

**Codec 纪律**：

| 规则 | 理由 |
|---|---|
| `Fixed` 一律编码为**整数千分比/万分比** | 避免 float 跨语言精度问题 |
| `enum` 一律编码为 `int` | GDScript 无枚举 |
| `EntityId<T>` 编码为其内部值 | GDScript 无泛型 |
| 编解码必须成对，用**往返测试**覆盖 | 编码错了 UI 会静默显示错误数据，极难排查 |
| 未知类型直接抛异常，不静默跳过 | 静默跳过 = UI 少播一个动画，事后无从查起 |

> **往返测试（Round-trip Test）是这套方案的质量底线**：
> `Decode(Encode(x)) == x`，对每个事件、每个命令都测一遍。
> 这是纯机械工作，AI 生成 + CI 跑，成本极低但能挡掉一大类诡异 bug。

## 八、常见坑清单

| 坑 | 症状 | 对策 |
|---|---|---|
| **改 C# 后编辑器不生效** | 逻辑没变，像缓存 | 需在编辑器中重新 Build（Godot 4 的 C# 需手动构建，无自动热重载） |
| **信号委托签名不匹配** | connect 无报错但不触发 | C# 信号委托名必须以 `EventHandler` 结尾，参数类型要匹配 |
| **GDScript 拿到的是 `Godot.Collections.Dictionary`** | 用原生字典 API 报错 | 注意命名空间，别混用 `System.Collections.Generic` |
| **导出时 .NET 运行时缺失** | 导出后启动崩溃 | 用含 .NET 的导出模板；确认目标平台支持（Steam 桌面端无问题） |
| **Autoload 单例跨场景重建** | 状态丢失 | Bridge 必须是 Autoload，且领域状态由应用层持有（不依赖 Godot 节点生命周期） |
| **float 跨语言精度** | 数值对不上但差得极小 | 领域层禁用 float，边界传整数千分比 |
| **事件顺序错乱** | 动画播放顺序不对 | 每个事件带 `seq`，GDScript 侧按 seq 排序后再播放 |

# 第7篇：draft-抽发

# 抽发上下文（Draft）

> **职责一句话**：从池子里按权重抽出一组候选，玩家择一（或跳过）。
> **状态**：🆕 本版新增（从原「肉鸽派发」中拆出）
> **不变量前缀**：`INV-D`

---

## 一、为什么单独拆出来

原「肉鸽派发」把"抽"和"装"混在一起。拆开后：

| | 抽发 Draft | 构筑 Progression |
|---|---|---|
| 本质 | **机制**（怎么抽） | **结构**（怎么装） |
| 消费者 | 技能三选一、遗物掉落、商店货架、宝箱、事件奖励、升级选择 | 只有单位槽位 |
| 变化频率 | 低（算法稳定） | 高（随内容迭代） |
| 核心资产 | 权重算法、保底、去重 | 槽位、升级阶梯 |

**收益**：一套算法 + 一套 UI 面板，吃下游戏里所有"给玩家几个选项挑一个"的场景。
这是爬塔类游戏出现频率最高的交互，值得单点做深。

---

## 二、核心模型

### 2.1 聚合根：`OfferPool`（报价池）

```
OfferPool（聚合根）
├─ poolId          : PoolId
├─ items           : OfferItem[]      ← 启动时从 Catalog 快照，之后不变
├─ weightRules     : WeightRule[]     ← 按 rarity / tag 的权重修正
├─ pityConfig      : PityConfig       ← 保底配置
├─ pityState       : PityState        ← 保底计数（跨多次抽取，随池持久化）
│
├─ GenerateOffer(request: DraftRequest) : OfferSet
└─ ApplySelection(offerId, selection)   : SelectionResolved
```

### 2.2 实体：`OfferSet`（一次报价）

```
OfferSet
├─ offerId     : OfferId
├─ poolId      : PoolId
├─ items       : OfferItem[]   （不重复，见 INV-D2）
├─ allowSkip   : bool
├─ source      : OfferSource   ← 溯源：战斗奖励 / 事件 / 商店 / 宝箱 / 升级
└─ state       : Pending | Selected | Skipped | Expired
```

### 2.3 值对象

| 值对象 | 字段 | 说明 |
|---|---|---|
| `OfferItem` | `itemId`（多态：`skill:xxx` / `relic:yyy`）、`itemType`、`rarity`、`weight`、`tags[]`、`payloadRef` | **Draft 不解析 payloadRef**，只做传递 |
| `DraftRequest` | `count`、`exclusions[]`、`constraints`（tag 过滤）、`seed` | 不可变 |
| `PityState` | `sinceLastRare`、`seenItemIds[]`、`drawCount` | 跨抽取持久化 |
| `SelectionResolved` | `selectedItemId \| null`、`commands[]` | 产出命令，交给应用层 |

### 2.4 领域服务

| 服务 | 职责 |
|---|---|
| `OfferGenerator` | 加权无放回抽样 + 去重 + 约束过滤 |
| `WeightCalculator` | 基础权重 × rarity 档 × 保底修正 × tag 修正 |
| `PityTracker` | 保底计数推进，触发保底时强制提升稀有度档 |

---

## 三、不变量

| # | 不变量 | 说明 |
|---|---|---|
| **INV-D1** | **确定性** | 同一 `poolState` + 同一 `request.seed` → 必然产生同一 `OfferSet`。可用于 bug 复现与回放 |
| **INV-D2** | **单次去重** | 一次 `OfferSet` 内 `itemId` 不重复 |
| **INV-D3** | **权重合法** | 池内所有 `weight ≥ 0`；生成时至少有一项有效权重 > 0，否则抛出异常而非静默返回空 |
| **INV-D4** | **保底单调** | `pityState.drawCount` 每次生成后严格 +1，不可回退、不可重置（重置只能通过显式配置） |
| **INV-D5** | **选择不可撤销** | `OfferSet` 一旦 `Selected`/`Skipped`，不可再变更 |
| **INV-D6** | **池封闭** | `OfferSet` 的所有项必须来自本 `OfferPool.items`，不得凭空生成 |

## 四、领域事件

| 事件 | 时机 | 消费者 |
|---|---|---|
| `OfferGenerated` | 生成报价 | UI（渲染面板）、Telemetry（记录候选分布） |
| `OfferItemSelected` | 玩家选择 | 应用层（分发后续命令：填槽位 / 加背包 / 扣金币） |
| `OfferSkipped` | 玩家跳过 | Telemetry（跳过率是重要的平衡信号） |
| `PityTriggered` | 保底触发 | UI（特效反馈）、Telemetry |

## 五、对外接口（OHS）

```
【入】DraftRequest
  {
    poolId,
    count        : int,        // 候选数量（通常 3）
    exclusions   : string[],   // 排除项（已满级的技能、已装备的唯一遗物…）
    constraints  : { requireTags?: string[], excludeTags?: string[], minRarity?, maxRarity? },
    seed         : long
  }

【出】OfferSet
  { offerId, items[], allowSkip, source }

【回执】SelectionResolved
  { selectedItemId?: string, skipped: bool, commands: Command[] }
```

**Draft 不认识任何具体业务类型。** 它只处理"带权重和标签的候选项"。
技能、遗物、药水都是 `OfferItem`，由应用层根据 `itemType` 分派后续处理。

## 二、核心模型

### 2.1 聚合根：`Build`（一个单位的构筑）

```
Build（聚合根）
├─ buildId     : BuildId
├─ unitId      : UnitId              ← 指向 Roster 中的英雄（只存 ID，不持有引用）
├─ pathwayId   : PathwayId           ← 途径，决定可选技能范围
├─ slots       : BuildSlot[]         ← 4 主动 + 4 被动
├─ upgradeStates : Map<skillDefId, UpgradeState>
│
├─ FillSlot(slotIndex, skillDefId)   : BuildChanged
├─ SwapSlot(a, b)                    : BuildChanged
├─ RemoveSlot(slotIndex)             : BuildChanged      【待补】是否需要移除功能
├─ ApplyDuplicate(skillDefId)        : DuplicateResolved ← 按 duplicatePolicy 分派
├─ Upgrade(skillDefId, tierChoice)   : BuildChanged
└─ ToSnapshot()                      : BuildSnapshot     ← 灌入战斗的产物
```

### 2.2 实体与值对象

| 类型 | 成员 | 说明 |
|---|---|---|
| **BuildSlot**（实体） | `index`、`kind`（active/passive）、`filledSkillDefId?` | 槽位本体 |
| **UpgradeState**（实体） | `skillDefId`、`currentTier`、`chosenModes[]` | 某技能的当前升级状态 |
| **BuildSnapshot**（值对象） | `unitId`、`slots[]`（已展开 tier 增量）、`frozenAt` | **不可变**，灌入战斗后不得修改 |
| **UpgradeTrack**（值对象） | `skillDefId`、`tiers[]` | 来自 Catalog，见你原有定义 |
| **LoadoutRequest**（值对象） | `unitDefId`、`ownedSkillIds[]`、`pathwayId` | Roster → Progression 的输入 |

### 2.3 领域服务：`BuildValidator`

集中承载所有校验规则，避免散落在聚合里：

| 校验 | 规则 |
|---|---|
| 槽位饱和 | 灌入战斗前，主动/被动槽必须填满（INV-P2） |
| 途径一致性 | 技能 pathway 必须等于单位 pathway，或在 `sharedAcross` 允许列表内 |
| 槽位唯一 | 同一 skillDefId 不可占两个槽（除非 `duplicatePolicy = stack`） |
| 档位边界 | `currentTier` ∈ [0, tiers.length - 1] |
| 快照冻结 | `BuildSnapshot` 生成后，源 Build 的变更不影响它 |

## 三、重复获得规则（duplicatePolicy，沿用你的定义）

| 取值 | 语义 | 触发的行为 |
|---|---|---|
| `upgrade` | 走 UpgradeTrack 升一档 | `UpgradeState.currentTier++`；若该档是形态选择，进入二选一报价（走 Draft） |
| `reject` | 丢弃，补抽 | 通知应用层重新发起一次 DraftRequest |
| `stack` | 叠加实例 | 多层 Grant，槽位占用数不变 |

> 【待补】`stack` 与"槽位唯一"约束（INV-P4）存在张力：stack 允许同技能多层，但槽位只有一个。
> 需要明确：stack 是"同一槽内累积多层 Grant"，还是"额外占一个槽"。
> **我的倾向**：同一槽内累积（槽位是稀缺资源，用槽位换叠层会让构筑空间坍缩）。

## 四、不变量

# 第9篇：run-跑图征程

# 跑图征程上下文（Run）

> **职责一句话**：一次爬塔从出发到结束的全部进程——地图、节点推进、资源、难度、结算。
> **状态**：🆕 本版新增
> **不变量前缀**：`INV-R`
> **地位**：单人模式的**主聚合**，是整个爬塔体验的骨架

---

## 一、职责边界

| 归 Run | 不归 Run |
|---|---|
| 地图生成与路径选择 | 战斗怎么打（战斗内核） |
| 节点类型与推进状态机 | 事件内容（Event 上下文） |
| 跨战斗持续的资源（金币/生命/药水/钥匙） | 英雄属性与背包（Roster） |
| 章节与难度曲线 | 技能从哪来（Draft） |
| 战斗触发与结算编排 | 战斗内的一切 |
| 整趟爬塔的种子管理 | 跨征程存档（元层） |

**一句话**：Run 是**流程编排者**，不是内容提供者。它知道"下一个节点是战斗还是商店"，但不知道战斗怎么打、商店卖什么。

---

## 二、核心模型

### 2.1 聚合根：`Run`

```
Run（聚合根）
├─ runId        : RunId
├─ runSeed      : RunSeed              ← 全局种子，派生一切
├─ actIndex     : int                  ← 当前章节
├─ state        : RunState             ← Active | InNode | Ended
├─ party        : PartyRef             ← 只存 ID，不持有 Roster 实体
├─ resources    : RunResources
├─ modifiers    : RunModifier[]        ← 整趟爬塔的全局修正（难度、祝福、诅咒）
├─ map          : MapGraph
├─ currentNodeId: NodeId?
├─ visitedPath  : NodeId[]             ← 已走过的路径（可回溯展示）
│
├─ Start(seed, partyRef, ruleset)      : RunStarted
├─ EnterNode(nodeId)                   : NodeEntered       ← 校验可达性
├─ ResolveCombat(summary: CombatSummary) : NodeResolved
├─ ResolveEvent(outcome)               : NodeResolved
├─ Advance(nextNodeId)                 : NodeEntered
├─ Abandon()                           : RunEnded
└─ End(result)                         : RunEnded
```

### 2.2 实体

| 实体 | 字段 | 说明 |
|---|---|---|
| **MapGraph** | `actIndex`、`layers[]`、`nodes[]`、`edges[]` | 章节地图，启动时生成后不变 |
| **MapNode** | `nodeId`、`layer`、`type`、`payloadId`、`visited` | 节点 |
| **RunResources** | `gold`、`hp`（若生命跨战斗持续）、`potions[]`、`keys`、`relicCharges` | 征程内资源 |
| **RunModifier** | `modifierId`、`source`、`params`、`duration` | 全局修正（难度诅咒、事件增益） |

### 2.3 值对象

| 值对象 | 取值 / 字段 | 说明 |
|---|---|---|
| `RunSeed` | `long` | 主种子，玩家可见、可分享 |
| `NodeType` | `battle` / `elite` / `boss` / `event` / `shop` / `rest` / `treasure` / `unknown` | 节点类型 |
| `RunState` | `Active` / `InNode` / `Victory` / `Defeat` / `Abandoned` | 状态机 |
| `MapEdge` | `from`、`to` | 路径边 |
| `ActConfig` | 层数、节点密度、类型分布权重、Boss 配置 | 章节参数（参数层） |

### 2.4 种子派生（ADR-07 落地）

```csharp
mapSeed     = SeedDeriver.Derive(runSeed, "map",    actIndex)
draftSeed   = SeedDeriver.Derive(runSeed, "draft",  nodeCounter)  // 每次抽取递增
eventSeed   = SeedDeriver.Derive(runSeed, "event",  nodeId)
shopSeed    = SeedDeriver.Derive(runSeed, "shop",   nodeId)
lootSeed    = SeedDeriver.Derive(runSeed, "loot",   nodeId)
combatSeed  = SeedDeriver.Derive(runSeed, "combat", actIndex, nodeId)
```

**每个子流独立计数**：抽卡次数不影响地图生成，战斗次数不影响商店货架。

## 三、节点流程状态机

```
                    ┌─────────┐
                    │ Active  │  玩家在地图上选下一个节点
                    └────┬────┘
                         │ EnterNode(nodeId)
                         ▼
                    ┌─────────┐
        ┌──────────│ InNode   │──────────┐
        │          └─────────┘          │
   type = battle/elite/boss        type = event/shop/rest/treasure
        │                               │
        ▼                               ▼
  启动战斗（交给战斗内核）          直接结算（Event / Draft）
        │                               │
        │ CombatEnded                   │ OutcomeResolved
        ▼                               ▼
   ┌─────────────────────────────────────────┐
   │ 结算：掉落报价 → 玩家选择 → 应用命令      │
   │      → 落盘 → 回到 Active                │
   └─────────────────────────────────────────┘
        │
        │ hp <= 0  →  Defeat
        │ 最终 Boss 击败 → Victory
        ▼
    ┌─────────┐
    │  Ended  │  → RunEnded 事件 → Meta / Telemetry
    └─────────┘
```

## 四、不变量

| # | 不变量 | 说明 |
|---|---|---|
| **INV-R1** | **地图连通性** | MapGraph 中，除最后一层外，每个节点至少有一条指向下一层的出边；每个非首层节点至少有一条入边 |
| **INV-R2** | **路径合法** | 只能从 `currentNode` 沿 `MapEdge` 走到直接后继，不得跳层或斜跨 |
| **INV-R3** | **Boss 唯一** | 每章最后一层有且仅有一个 Boss 节点到达该层后，下一步只能进入 Boss |
| **INV-R4** | **终局不可推进** | `state = Ended` 后，任何 `EnterNode` / `Advance` 必须被拒绝 |
| **INV-R5** | **死亡即终止** | 队伍生命归零 → Run 立即转为 `Defeat`，不得继续推进 |
| **INV-R6** | **种子确定性** | 同 `runSeed` + 同操作序列 → 同地图、同掉落、同事件（依赖全局随机治理） |
| **INV-R7** | **节点幂等** | 同一 `nodeId` 的奖励只能结算一次；重复提交必须被拒绝 |
| **INV-R8** | **资源非负** | `gold` / `hp` / `keys` 任何时刻不得为负；扣减操作必须先校验余额 |

# 第10篇：event-事件

# 事件上下文（Event）

> **职责一句话**：非战斗节点的内容——给玩家一段情境、几个选项，产出一组结果命令。
> **状态**：🆕 本版新增
> **不变量前缀**：`INV-EV`
> **设计要点**：**事件是纯数据驱动的**，上下文本身极薄，全部复杂度在内容数据里

---

## 一、设计原则：极薄上下文 + 极厚数据

事件是爬塔游戏里内容量最大、逻辑最简单的部分（几十到上百个事件，每个都是"文本 + 选项 + 结果"）。

因此：

| 放在上下文里 | 放在 Catalog 数据里 |
|---|---|
| 条件求值引擎 | 具体事件文本 |
| 选项筛选逻辑 | 选项与条件 |
| 结果掷骰 | 结果权重与命令 |
| 一次性/去重管理 | 事件池权重 |

**推论**：Event 上下文代码量应该很小（几百行），但它驱动的 JSON 数据可能有几千行。
**这正是最适合 AI 批量生产的部分**：结构固定、规则明确、可自动校验。

---

## 二、核心模型

### 2.1 聚合根：`EventInstance`

```
EventInstance（聚合根）
├─ instanceId   : EventInstanceId
├─ eventDefId   : EventDefId        ← 指向 Catalog
├─ runId        : RunId             ← 只存 ID
├─ nodeId       : NodeId
├─ state        : Pending | OptionChosen | Resolved
├─ availableOptions : OptionId[]    ← 已按条件筛出的可见选项
├─ chosenOption : OptionId?
├─ resolvedOutcome : OutcomeId?
│
├─ Evaluate(context: EventContext)   : 筛选可见选项
├─ Choose(optionId, seed)            : EventResolved   ← 掷骰选结果，产出命令
└─ Resolve()                         : EventResolved
```

### 2.2 定义态（Catalog 侧）

```
EventDef
├─ id, title, text, artRef
├─ conditions[]     : Condition[]    ← 出现条件（章节 / 生命低于 X / 持有某遗物…）
├─ weight           : int            ← 在事件池中的权重
├─ onceOnly         : bool           ← 一次征程是否只出现一次
├─ minAct / maxAct  : int?
└─ options[]
     ├─ id, text
     ├─ requirements[] : Condition[]  ← 选项可见条件（需 50 金币 / 需某属性…）
     ├─ previewHint    : string       ← 模糊结果提示（杀戮尖塔式："你感到力量涌动"）
     └─ outcomes[]     : Outcome[]
          ├─ id, weight
          └─ commands[] : Command[]   ← 结果命令（见 §四）
```

### 2.3 值对象

| 值对象 | 字段 | 说明 |
|---|---|---|
| `Condition` | `type`、`params`、`negated?` | 声明式条件，由求值引擎解释 |
| `EventContext` | `runState`、`partySummary`、`resources`、`flags` | 求值上下文（只读投影，不是聚合本身） |
| `EventResolved` | `outcomeId`、`text`、`commands[]` | 结果 + 命令 |

---

## 三、不变量

| # | 不变量 | 说明 |
|---|---|---|
| **INV-EV1** | **选项可见性** | 只有 `requirements` 全部满足的选项才进入 `availableOptions`；UI 不得展示被过滤的选项 |
| **INV-EV2** | **一次性结算** | `state = Resolved` 后，任何 `Choose` 必须被拒绝（防重复领取奖励） |
| **INV-EV3** | **引用完整性** | `EventDef` 引用的所有 id（遗物、技能、资源类型）必须存在于 Catalog |
| **INV-EV4** | **条件可判定** | 所有 `Condition` 在 `EventContext` 中必须能求出确定布尔值，不得出现未定义行为 |
| **INV-EV5** | **命令封闭** | Event 上下文**不得直接修改**任何其他聚合；所有副作用必须表达为 `Command[]` |

> **INV-EV5 是最重要的一条。** 它让事件数据变成纯声明式，可以被 AI 批量生成、非程序员编辑、静态校验。
> 一旦允许事件直接操作 Hero，事件数据就变成了代码，全部好处消失。

---

## 四、命令目录（Command Catalog）

事件的全部副作用通过这组命令表达。**命令是应用层可分发的最小原子操作**。

| 命令 | 参数 | 目标聚合 |
|---|---|---|
| `ModifyResource` | `resourceType`、`delta` | Run |
| `ModifyHeroHp` | `heroId`、`delta` | Roster |
| `GrantExperience` | `heroId`、`amount` | Roster |
| `GrantItem` | `itemId`、`count` | Roster（Inventory） |
| `RemoveItem` | `itemId`、`count` | Roster（Inventory） |
| `GrantDraftOffer` | `poolId`、`count` | Draft → 链式触发报价 |
| `GrantSkill` | `skillDefId`、`targetHeroId` | Progression（直接填槽或走报价） |
| `UpgradeSkill` | `skillDefId`、`tier` | Progression |
| `StartCombat` | `enemyGroupId` | Run → 战斗内核 |
| `AddRunModifier` | `modifierId`、`params` | Run |
| `RecruitHero` | `heroDefId` | Roster |
| `SetFlag` | `flagId`、`value` | Run（用于后续事件条件） |
| `EndRun` | `result` | Run |

**命令执行语义**：
```
应用层 for cmd in outcome.commands:
    加载目标聚合 → 校验 → 应用 → 提交
全部成功 = 事务提交；任一失败 = 整体回滚
```

【待补】命令执行失败的处理策略（回滚全部 vs 跳过失败项）。**倾向整体回滚**——部分生效的事件结果会让状态难以预测。

## 五、领域事件

| 事件 | 时机 | 消费者 |
|---|---|---|
| `EventTriggered` | 进入事件节点 | UI（展示）、Telemetry |
| `EventOptionChosen` | 玩家选择 | Telemetry（选项分布是重要平衡数据） |
| `EventResolved` | 结果掷骰完成 | 应用层（分发命令）、UI（展示结果） |

## 六、条件求值引擎

条件用声明式表达，避免事件数据里出现代码：

```json
{ "type": "ResourceAtLeast", "resource": "gold", "value": 50 }
{ "type": "HeroHpPercentBelow", "value": 0.5 }
{ "type": "HasItem", "itemId": "relic_blood_vial" }
{ "type": "FlagEquals", "flag": "met_merchant", "value": true }
{ "type": "ActAtLeast", "value": 2 }
{ "type": "Not", "condition": { ... } }
{ "type": "AllOf", "conditions": [...] }
{ "type": "AnyOf", "conditions": [...] }
```

**实现**：一个 `switch` + 一组 `IConditionEvaluator`。新增条件类型只需加一个实现类 + 一份 JSON Schema 描述。

> **JSON Schema 描述是关键**：有了它，AI 生成事件数据时可以自动校验，也能让编辑器给出自动补全。
> 这让"AI 批量生成上百个事件"从愿望变成可执行的流程。

# 第11篇：roster-名册与队伍

# 战外名册与队伍上下文（Roster）

> **职责一句话**：**本次征程**的队伍、背包、站位与技能编排——战外成长的全部抓手。
> **状态**：🆕 本版新增 · **已按 ADR-09 定为征程级生命周期**
> **不变量前缀**：`INV-RO`
> **生命周期**：★ **征程级** —— 随一次爬塔创建，随该次爬塔结束（通关或死亡）清空。**战斗之间不清空。**
> **术语**：见 [00-术语对照](../00-术语对照.md)
> **注意**：与战斗内核的「编队 Formation」是**完全不同的东西**，勿混淆

---

## 〇、生命周期为什么是"征程级"（关键，别读错）

**先澄清一个会造成灾难性误解的点**：本篇的"战外"指**一场战斗之外**，不是"一次爬塔之外"。
队伍、背包、技能编排、站位在**整趟爬塔过程中持续存在**，只在爬塔结束（通关或死亡）时才清空。

```
一次爬塔 Run
│
├─ 战斗① ─▶ 战外（领奖励·装技能·调队伍·买东西）─▶ 战斗② ─▶ 战外 ─▶ … ─▶ 通关 / 死亡
│              ↑                                    ↑
│              队伍·背包·站位 在战斗之间完全持续      不是每场战斗后重置！
│
└─ 只有爬塔结束，Roster 才销毁
```

> ⚠️ 上一版写的"局末清空"有严重歧义：按"局 = 一场战斗"的读法，
> 会变成**每打完一场战斗队伍就重置**——与实际需求完全相反。已按新术语修正。

### 为什么不是"跨征程持久"

原设计里 Roster 是跨征程持久的"玩家名册"（英雄等级、装备、已学技能永久留存）。
**已定元层不存在永久成长**，于是"跨征程名册"失去立足点——跨征程只剩一个解锁 id 集合，
不值得为它单独立上下文。

| 原设计 | 现设计 |
|---|---|
| 跨征程持久的 `Hero`（含 level/xp/装备） | ❌ 取消 |
| 跨征程持久的 `Inventory` | ❌ 取消 |
| — | ➕ `Meta.UnlockSet`：就是一组 id，属**元层** |
| `Party`（队伍） | ✅ 保留，**生命周期 = 一次征程** |
| `Inventory`（背包） | ✅ 保留，**生命周期 = 一次征程** |

**收益**：少一套持久化、少一套迁移、少一类"为什么我上次的装备没了"的客诉。
而且爬塔游戏的正确行为本来就是"每趟爬塔从零开始"——这次架构和产品语义真正对齐了。

## 一、与战斗内核「编队」的区分

| | Roster（本篇） | 战斗内核·编队 |
|---|---|---|
| 场景 | **战外**（本次征程内，进入战斗之前） | **战内**（一场战斗之中） |
| 语义 | 玩家编排意图（谁在第几排） | 实际占位（格子、坐标） |
| 约束 | 玩家偏好，可随意调整 | 唯一占位、队列坍缩、移动规则 |
| 生命周期 | **征程级**（跨战斗持续，爬塔结束才清） | 一场战斗结束即销毁 |
| 聚合 | 独立聚合 | Combat 聚合内的分层 |

**两者之间通过 ACL 翻译**：`Party.formation`（玩家意图）→ `Coordinate`（战斗格子）。
**不要共享同一个 `Coordinate` 类型**（见 01 篇 §五的陷阱说明）。

## 二、核心模型（三个聚合）

### 2.1 聚合一：`Hero`（征程内英雄实例）

```
Hero（聚合根）   ← 征程级实体：整趟爬塔持续存在，爬塔结束时随 Run 一起清空
├─ heroId          : HeroId           ← 本次征程内唯一，跨征程不保留
├─ heroDefId       : HeroDefId        ← 指向 Catalog（这个是持久的）
├─ baseAttributes  : AttributeBlock   ← 来自 HeroDef 的基础属性
├─ learnedSkillIds : SkillDefId[]     ← 本次征程中获得的技能（→ 交给 Progression 装槽）
│
├─ LearnSkill(skillId) : SkillLearned
└─ ComputeAttributes() : AttributeBlock   ← 基础属性 + 遗物修正（无等级、无装备）
```

> **没有 `level` / `xp` / `equipment`。**
> 无永久成长后，英雄的成长全部来自三处：**获得技能（Progression 装槽）+ 技能升档（UpgradeTrack）+ 遗物修正（Inventory）**。
> 这三者已经提供了足够成长感；等级与装备只会给 `StatProvenance` 多加两条来源，却不增加任何决策深度。
> 【待确认 Q9 / Q11】

### 2.2 聚合二：`Inventory`（背包）

```
Inventory（聚合根）
├─ inventoryId  : InventoryId
├─ relics       : RelicInstance[]    ← 遗物（全局生效，通常无上限或高上限）
├─ items        : ItemStack[]        ← 消耗品，有数量
├─ capacity     : int                ← 消耗品格数上限
│
├─ Add(itemId, count)     : ItemAcquired      （校验容量）
├─ Remove(itemId, count)  : ItemConsumed
├─ AddRelic(relicId)      : RelicAcquired     （校验唯一性）
└─ QueryRelicEffects()    : Modifier[]        ← 供属性计算与战斗 ACL 使用
```

### 2.3 聚合三：`Party`（队伍）

```
Party（聚合根）
├─ partyId      : PartyId
├─ members      : PartyMember[]      ← 有序，最多 N 人
├─ formation    : FormationLayout    ← 初始站位（值对象）
├─ leaderId     : HeroId
│
├─ AddMember(heroId)      : PartyChanged      （校验人数上限 / 重复）
├─ RemoveMember(heroId)   : PartyChanged
├─ SetPosition(heroId, pos) : PartyRearranged
├─ Reorder(from, to)      : PartyRearranged
└─ ToCombatParty()        : CombatPartyInput  ← 供 ACL 组装 CombatSetup
```

### 2.4 值对象

| 值对象 | 字段 | 说明 |
|---|---|---|
| `FormationLayout` | `positions: Map<HeroId, SlotIndex>` | 玩家编排，**只是意图**，不含战斗规则 |
| `SlotIndex` | `row`、`col` | 队伍站位格（**战外**概念，≠ 战内 `Coordinate`） |
| `ItemStack` | `itemId`、`count` | 可堆叠消耗品 |
| `RelicInstance` | `relicDefId`、`charges?` | 遗物（可带充能） |
| `AttributeBlock` | 各属性值 | 属性聚合结果 |
| `CombatPartyInput` | `units[]`、`initialSlots`、`relicModifiers` | 交给 ACL 的输入 |

## 六、与战斗内核的边界

```
Roster.Party ──┐
Roster.Hero  ──┼──▶ [ACL: CombatSetupFactory] ──▶ CombatSetup ──▶ 战斗内核
```

## 二、核心模型

## 三、同步协议（ADR-03：确定性锁步）

### 3.1 流程

```
回合 N：
  1. 本地生成操作 ops（无需等待对手）
  2. 广播 InputRecord { turnNo: N, playerId, ops, inputHash }
  3. 收到对手的 InputRecord(turnNo: N)
  4. 按**固定顺序**（先 host 后 guest）应用两个输入 → 推进一回合
  5. 每 K 回合广播 stateHash，不一致 → 失步处理
```

### 3.2 关键设计点

| 问题 | 对策 |
|---|---|
| **输入顺序** | 必须固定（如按 playerId 排序），否则双方应用顺序不同 → 分叉 |
| **随机性** | 所有随机走 `matchSeed` 派生的子流，双方派生结果必然一致 |
| **失步检测** | 定期比对 stateHash（对领域状态做确定性哈希） |
| **失步恢复** | 以完整 `inputLog` 为准，重放至当前回合 |
| **断线** | 等待超时 → 判负或托管 AI（可配置） |
| **重连** | 下发 `matchSeed` + `inputLog` → 本地重放到当前状态 |
| **隐藏信息** | ⚠️ 见 §3.3 |

### 3.3 隐藏信息问题（真正的难点）

锁步意味着**双方本地都有完整状态**，如果游戏存在隐藏信息（手牌、牌库顺序、未翻开的内容），本地可以直接读到对手的手牌。

| 方案 | 复杂度 | 说明 |
|---|---|---|
| **A. 接受它** | 零 | 若你的战斗全是公开信息（4+4 技能槽位明牌），**没有这个问题** |
| B. 承诺-揭示 | 中 | 隐藏信息用哈希承诺，揭示时验证 |
| C. 服务器权威 | 高 | 只给客户端该看的部分 |

**已确认（ADR-10，2026-09-04）**：无牌库、无抽牌堆，固定 4 主动 + 4 被动**全公开**槽位。
→ **方案 A：接受它。隐藏信息问题不存在，锁步零障碍。**

这把 M8 的难度砍掉了一大块——原本可能需要的"承诺-揭示"协议或服务器权威都不必做了，
P2P 锁步可以一路走到底。

### 3.4 连带影响：完全信息博弈

没有隐藏信息，PvP 就变成了**完全信息博弈**（类似国际象棋，而非扑克）。

| | 影响 | 应对 |
|---|---|---|
| ✅ 好处 | 策略纯粹，比拼计算深度而非运气；无发牌运气投诉 | — |
| ⚠️ 顾虑 | 双方都能算清对方全部技能与冷却，可能退化为"最优解对拼" | 【待补】可选：隐藏的备选槽位、赛前禁用、迷雾机制 |

# 第13篇：meta-元进度

# 元层上下文（Meta）

> **职责一句话**：**跨征程永久持久**的一切——解锁进度、爬塔排名、成就、统计、图鉴、设置、难度等级。
> **状态**：🆕 本版新增 · 排期 M7（难度等级建议提到 M5）
> **不变量前缀**：`INV-ME`
> **生命周期**：★ **元层** —— 换一次爬塔也还在，随账号永久持久
> **术语**：见 [00-术语对照](../00-术语对照.md)（"跨局"一律改称"跨征程"）
> **定位**：支撑域，**能省则省**，不要在这里过度设计

---

## 〇、本层包含什么（对应你说的"爬塔排名、卡牌解锁进度"）

| 你说的 | 落在哪 | 说明 |
|---|---|---|
| **卡牌/技能解锁进度** | `Unlock[]` | 跨征程累积，解锁后新内容进入后续爬塔的候选池 |
| **爬塔排名** | `Statistics` + `Leaderboard` | 对接 Steam 排行榜（层数 / 分数 / 每日挑战） |
| 成就 | `Achievement[]` | 对接 Steam Achievements |
| 图鉴 | `Codex` | 见过/用过的内容收集度 |

**这一层就是"换一趟爬塔也还在的东西"，其余全部随爬塔清空。**

---

## 一、设计原则：克制

爬塔类游戏的元进度是一把双刃剑：

| 做法 | 后果 |
|---|---|
| 元层提供**数值成长**（永久加攻击力） | 稀释爬塔本身的构筑乐趣；新玩家被老玩家进度碾压；平衡难度曲线崩坏 |
| 元层只做**内容解锁**（新英雄、新技能、新遗物进入池子） | 增加长期目标感，不破坏单次爬塔平衡 ✅ |
| 元层完全不存在 | 长期留存弱，但首发可接受 |

> **已定（2026-09-04，ADR-09）**：**不做永久数值成长。**
> Meta 只保留：**解锁 + 成就 + 统计 + 图鉴 + 设置 + 难度等级**。

理由（已确认）：
1. 爬塔的核心乐趣是"每趟爬塔从头开始的构筑博弈"，永久数值成长会稀释它
2. 数值成长意味着你要平衡两条曲线（单趟爬塔曲线 × 元层成长曲线），工作量翻倍且容易崩
3. 解锁型元进度对平衡的污染可控——新技能进池子，仍然受单次爬塔的抽发规则约束
4. Steam 成就本身就能提供足够的目标感

### 唯一的例外：难度等级（Ascension 式）

**推荐做**，它和"数值成长"有本质区别：

| | 永久数值成长 | 难度等级 |
|---|---|---|
| 玩家获得 | 被动变强 | 主动选择变难 |
| 对平衡的影响 | 污染默认体验 | **不污染**（默认体验不变） |
| 实现成本 | 高（要平衡两条曲线） | 低（只是给 Run 加一组 modifier） |
| 长线留存 | 弱（变强后就没挑战了） | **强**（这是杀戮尖塔长线留存的核心） |

> 难度等级本质是"玩家主动开启的 modifier 组"，不是成长。
> 它不进入 `PlayerProfile` 的属性系统，只是 Run 启动参数的一个额外输入。

## 二、核心模型

### 2.1 聚合根：`PlayerProfile`

```
PlayerProfile（聚合根）   ← 跨征程持久的**全部**内容，很轻
├─ profileId        : ProfileId
├─ unlocks          : Unlock[]          ← 解锁进度（英雄/技能/遗物/难度）
├─ achievements     : Achievement[]     ← 成就状态
├─ statistics       : Statistics        ← 累计统计
├─ leaderboard      : LeaderboardEntry[] ← 爬塔排名记录（最佳层数/分数/每日挑战）
├─ codex            : Codex             ← 图鉴（见过/用过的内容）
├─ settings         : Settings          ← 设置（语言、音量、辅助功能）
├─ difficultyLevel  : int               ← 难度等级（玩家主动选择，0..N）
│
├─ RecordRun(summary: RunSummary)     : RunRecorded
├─ EvaluateUnlocks()                  : Unlocked[]
├─ GrantAchievement(id)               : AchievementGranted
├─ MarkCodexSeen(entryType, id)       : CodexUpdated
├─ SetDifficulty(level)               : DifficultyChanged
└─ UpdateSettings(settings)           : SettingsChanged
```

> **这里没有任何"单次爬塔内"的数据。**
> 队伍、背包、金币、技能编排全部是**征程级**，随一次爬塔创建、随该次爬塔结束清空。
> 跨征程持久的只有上面这几样——全都是"元数据"，没有一个会影响战斗数值。

### 2.2 实体 / 值对象

| 类型 | 字段 | 说明 |
|---|---|---|
| `Statistics`（实体） | `totalRuns`、`victories`、`deaths`、`bestAct`、`totalPlaytime`、`favoriteSkills[]` | 累计统计 |
| `Unlock`（实体） | `unlockId`、`type`（hero/skill/relic/difficulty）、`targetId`、`unlockedAt` | 解锁项 |
| `Achievement`（实体） | `achievementId`、`state`（locked/unlocked）、`progress?` | 成就（对接 Steam） |
| `Codex`（实体） | `entries: Map<entryId, SeenState>` | 图鉴 |
| `RunSummary`（值对象） | `runSeed`、`result`、`actReached`、`turns`、`buildSummary`、`stats` | 一次征程的摘要（供统计与展示） |

| # | 不变量 | 说明 |
|---|---|---|
| **INV-ME1** | **解锁不可逆** | 解锁条件一旦满足并应用，不得回滚（即使触发条件后来不再成立） |
| **INV-ME2** | **成就唯一** | 同一 `achievementId` 只能授予一次；重复调用必须幂等 |
| **INV-ME3** | **单向依赖** | Meta **不得反向影响**进行中的 Run。解锁的新内容只在**下一次爬塔**生效 |

> 直接违反 INV-R6。解锁必须"下一次爬塔才生效"——不能中途往这趟爬塔的池子里塞新技能。

## 三、`Fixed` 定点数（重点）

### 3.1 为什么必须有

跨平台浮点差异是确定性架构的头号杀手：

```
0.1 + 0.2 != 0.3            （二进制浮点）
Math.Pow / Math.Sin 在不同平台末位可能不同
→ 伤害差 1 点 → 战斗分叉 → 锁步失步 → 回放失效
```

**对策**：影响结果的所有计算走定点数，表现层再转 float。

### 3.2 接口设计

```csharp
public readonly struct Fixed : IEquatable<Fixed>, IComparable<Fixed>
{
    private readonly long _raw;              // 缩放因子 1 << 16
    public static readonly Fixed Zero, One;

    public static Fixed FromInt(int v);
    public static Fixed FromRatio(int numerator, int denominator);
    public static Fixed FromPermille(int permille);   // 千分比，配表友好

    public Fixed Add(Fixed o);
    public Fixed Sub(Fixed o);
    public Fixed Mul(Fixed o);               // (a * b) >> 16，注意溢出
    public Fixed Div(Fixed o);
    public Fixed Clamp(Fixed min, Fixed max);

    public int ToIntRound();                 // 取整时机必须统一
    public float ToFloat();                  // 只在表现层用
}
```

### 3.3 纪律

| 规则 | 说明 |
|---|---|
| 领域层**禁止出现** `float` / `double` | 用架构守卫测试扫描 |
| 取整时机统一 | 全部在"应用到属性时"取整一次，中间过程保持定点精度 |
| 溢出防护 | `Mul` 内部用 `Int128` 或先移位再乘 |
| 配表用千分比/万分比整数 | 避免 JSON 里出现 `0.15` 这种浮点 |

## 四、`Condition` 声明式条件（第二个重点）

Event 的条件、Meta 的解锁条件、Draft 的约束过滤，本质都是"对上下文求值一个布尔表达式"。统一实现，三处复用。

```json
{ "type": "ResourceAtLeast", "resource": "gold", "value": 50 }
{ "type": "HasItem",        "itemId": "relic_x" }
{ "type": "ActAtLeast",     "value": 2 }
{ "type": "Not",     "condition": { ... } }
{ "type": "AllOf",   "conditions": [ ... ] }
{ "type": "AnyOf",   "conditions": [ ... ] }
```

```csharp
public interface IConditionEvaluator<in TContext>
{
    string Type { get; }
    bool Evaluate(Condition condition, TContext context);
}
```

**收益**：
- 一份 JSON Schema，AI 生成内容时可自动校验
- 编辑器可自动补全
- 新增条件只加一个实现类，不改任何已有代码

> 这套东西同时服务于"AI 批量生成事件/解锁条件"——
> **结构化的声明式表达，是让 AI 产出可靠内容的必要前提**。自由格式的自然语言规则无法自动校验。

## 五、不变量

| # | 不变量 | 说明 |
|---|---|---|
| **INV-SK1** | **纯净性** | 共享内核不得持有任何业务规则；不得引用任何具体上下文的命名空间 |
| **INV-SK2** | **确定性** | 所有计算必须跨平台、跨进程完全一致；禁止依赖字典遍历顺序、字符串哈希、浮点 |
| **INV-SK3** | **不可变** | 共享内核的值对象全部不可变（`readonly struct` / 只读属性） |

## 六、审查流程（建议）

共享内核的每次改动，走一个轻量但明确的流程：

```
改动提议 → 说明「为什么它必须在共享内核，而不是某个上下文内部」
        → 检查四条准入标准
        → 至少两人（或你 + AI 交叉复核）确认
        → 更新本篇清单
```

**没有流程的话，共享内核会在半年内变成垃圾桶**——所有"不知道放哪"的东西都会被塞进来。
到那时它就不再是共享内核，而是一个谁都不敢改的巨型依赖中心。
